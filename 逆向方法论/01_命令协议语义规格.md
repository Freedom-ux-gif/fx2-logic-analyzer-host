# 命令协议语义规格

> 本文档是可实现规格：目标是让任何工程师或 AI 读完，都能独立重写一套采集代码，而不必接触原厂程序。
>
> 以上规格由本项目独立整理，可据此重写实现，无需接触原厂程序。

文中统一术语：**明文**指设备内部、混淆前的值；**线上字节**指 USB 线上真正传输、混淆后的值。二者不能混用。

---

## 1. 命令结构

启动采集的命令只有 **2 字节**：

```
{ 0x01, delay }
```

- 第 1 字节 `0x01` 是固定的命令类别标识。
- 第 2 字节 `delay` 是分频参数，决定采样率。

`delay` 由采样率换算而来，FX2 使用 48 MHz 时钟分频：

```
delay = 48000000 / rate - 1
```

其中 `rate` 是每秒采样数（Hz），结果整除后减一，再取低 8 位。这条公式已用 8 kHz 方波交叉验证：12/8/4/1 MHz 四档下主 run 长度比为 750:500:250:63，前三者严格等于 12:8:4，证实分频算法正确。

命令**不能明文发送**。明文写入 USB 端点虽然会成功返回字节数，但设备完全沉默不出数据；只有发送混淆后的密文，设备才立刻吐出数据流。所以真正在线上出现的是第 3 节的混淆结果。

---

## 2. 有状态混淆算法

线上字节是明文字节经过一个有状态变换得到的。它**不是**固定替换表，必须用状态机实现。

- 初始状态：`A = 0x54`（上一个密文字节），`B = 0x9B`（上一个明文字节）。
- 对每个明文字节 `p`，依次执行 10 步 8 位变换得到密文 `t`。
- 每处理完一个字节，更新状态 `B, A = p, t`，即 B 变为刚处理的明文，A 变为刚产生的密文。
- 因为状态持续串联，同一个明文在不同位置会得到不同密文——这正是不能用无状态替换表的原因。
- 所有运算都在 8 位内进行，每一步后取低 8 位（掩码 `0xFF`）。

逆变换（把线上字节还原成明文）是同一状态机的反向运算，状态更新规则一致（`B, A = p, c`，其中 c 是当前密文字节），用于分析应答；采集实现只需要正向。

混淆器还有别的分支（例如基于 32 位 LFSR 的密钥流、置位标志分支），但写命令走的是上面这条固定变换分支；LFSR 分支会改变结果，这也是"线上字节不能固定等于某个明文常量"的原因。本项目只使用固定变换分支。

## 3. 完整 Python 实现

以下实现逐字对应 `交接手册/H1_硬件与协议.md` 第 3.3 节，可直接在 Python 3 运行：

```python
def obfuscate(plain):
    out, A, B = [], 0x54, 0x9B
    for p in plain:
        t = A ^ p
        t ^= 0x2B
        t = (t - 5) & 0xFF
        t ^= 0x35
        t = (t - 0x39) & 0xFF
        t ^= B
        t ^= 0x5A
        t = (t + 0x50) & 0xFF
        t ^= 0x38
        t = (t - 0x45) & 0xFF
        out.append(t)
        B, A = p, t
    return bytes(out)
```

要点复核：

- 初值 `A=0x54` 是"上一个密文字节"，`B=0x9B` 是"上一个明文字节"；
- 10 步变换顺序固定，异或常数依次为 `0x2B / 0x35 / B / 0x5A / 0x38`，算术为减 5、减 0x39、加 0x50、减 0x45；
- `B, A = p, t` 必须是**状态串联**，写成在同一步里同步赋值，不能先改 A 再改 B；
- 返回值是 `bytes`，可直接写入 USB 端点。

## 4. 10 档采样率的 delay 与加密后字节

明文命令始终是 `{0x01, delay}`。下表给出每一档的采样率、delay（十进制与十六进制）、明文命令、以及对应的加密后线上字节。

| 采样率 | delay（十进制） | delay（hex） | 明文命令 | 加密后（线上） |
|---|---|---|---|---|
| 24 MHz | 1 | 0x01 | `01 01` | `d5 d5` |
| 16 MHz | 2 | 0x02 | `01 02` | `d5 d5` |
| 12 MHz | 3 | 0x03 | `01 03` | `d5 e2` |
| 8 MHz | 5 | 0x05 | `01 05` | `d5 d4` |
| 4 MHz | 11 | 0x0b | `01 0b` | `d5 da` |
| 2 MHz | 24 | 0x18 | `01 18` | `d5 e6` |
| 1 MHz | 47 | 0x2f | `01 2f` | `d5 8e` |
| 500 kHz | 95 | 0x5f | `01 5f` | `d5 fe` |
| 250 kHz | 191 | 0xbf | `01 bf` | `d5 9e` |
| 200 kHz | 239 | 0xef | `01 ef` | `d5 4e` |

注意：24 MHz 与 16 MHz 的加密后两字节都是 `d5 d5`——这是状态串联下的正常现象，不要怀疑抄错。实际采集前，用第 6 节自检命令核对任何一档。

## 5. 6 条验证向量

下表是判定"你的混淆算法实现正确"的黄金向量，全部在本机用第 3 节代码实跑复算通过。

| 明文（hex） | 加密后（hex） | 来源 / 说明 |
|---|---|---|
| `01` | `d5` | sigrok 文档记载"新固件首字节 0xd5" |
| `01 03` | `d5 e2` | 设备对 `0x58` 命令的应答比对 |
| `01 05` | `d5 d4` | 反汇编复现，与设备行为一致 |
| `01 2f` | `d5 8e` | 实测可用：明文不出数据，密文立刻出数据 |
| `7d 55` | `61 d4` | 原厂软件官方抓包 |
| `01 0b` | `d5 da` | 4 MHz 采集实测：明文 `010b`→线上 `d5da` |

自检命令（把第 3 节的函数粘进 `python -I` 会话后执行）：

```

        t = A ^ p; t ^= 0x2B; t = (t-5)&0xFF; t ^= 0x35; t = (t-0x39)&0xFF
        t ^= B; t ^= 0x5A; t = (t+0x50)&0xFF; t ^= 0x38; t = (t-0x45)&0xFF

```

## 6. 采集时序（6 步，顺序不可调换）

```
1. open_dev()     打开设备、设管道策略（超时 / RAW_IO / 忽略短包）
2. drain          读空数据端点残留（8 次 100ms 超时读，丢掉上次采集的尾巴）
3. 起读线程       在数据端点上阻塞等数据（先就位，但还没发命令）
4. 发命令         写命令端点，内容是加密后的 {0x01, delay}
5. 收数据         读线程循环按 64KB 块收进 chunks
6. 停止           置 stop 标志、join 线程、拼接 chunks
```

为什么顺序不能反，有两个原因：

**原因一：FIFO 溢出（决定第 3 步必须在第 4 步之前）。** 设备收到启动命令后会立刻开始向 FX2 的 FIFO 填入采样数据，而 FIFO 容量有限。如果这时主机端还没有线程在阻塞读取，填入的数据会持续堆积，FIFO 满后新数据覆盖旧数据。实测：先发命令再起线程，开头几百毫秒的数据会丢失——这段时间足够 FIFO 溢出好几次。因此读线程建立后还会额外 `sleep(0.2)`，确保它真正进入阻塞读状态，然后才写命令。

**原因二：残留数据（决定第 2 步 drain 必须在发命令之前）。** 上一次采集可能留下未读干净的数据残留在数据端点；不排空的话，这些旧字节会混进本次结果开头，造成"前几个样本对不上信号"的假象。drain 用 100ms 短超时读 8 次，读不到就放弃，不阻塞主流程。

第 1 步的管道策略同样是为了这两个目的：超时避免读线程永久卡死，RAW_IO 与忽略短包保证批量传输的原始字节流完整。

## 7. 数据格式

每次从数据端点读回的是**裸字节流**，每个字节代表一个采样时刻的 8 个通道电平：

```
bit7  bit6  bit5  bit4  bit3  bit2  bit1  bit0
 CH7   CH6   CH5   CH4   CH3   CH2   CH1   CH0
```

- 通道映射 **CHn → bitn**（CH0 对应 bit0，CH7 对应 bit7）。
- `bit=1` 表示该通道此刻为高电平，`bit=0` 为低电平。
- 未接线的通道读作高（内部上拉），所以空闲时字节常为 `0xFF`。
- 注意：这个映射与 sigrok 文档记载的"Probe 1 在最高位、Probe 8 在最低位"完全相反，是本机克隆板实测结果，不要照搬 sigrok 的说法。

解析示例：采到 `FF FE FF FE FF FF`，取 bit0 得到 `1 0 1 0 1 1`，说明 CH0 上有一个方波。取单通道序列时按 `(byte >> n) & 1` 提取第 n 位即可。

## 8. 边界条件清单

| 情形 | 如何判断 | 处理 |
|---|---|---|
| 空数据 | 命令已发、读线程就位，但按预期时长收不到任何字节；各档理论带宽 = 8 通道 × 采样率，可据此估算应有字节数 | 先用第 5 节自检命令核对命令是否正确加密；再检查设备是否已初始化 |
| 超时（错误码 121，`ERROR_SEM_TIMEOUT`） | 读/写端点报 121 | 两种原因：设备未初始化（缺数据端点），或发了明文命令设备不响应。分别按下面两项处理 |
| 端点缺失 | 枚举到的端点表里没有数据端点 `0x82`；典型表现是 alt setting 为 1、端点表形如 `0x01 0x81 0x02 0x04 0x86 0x88` | 设备未初始化：先用原厂软件识别一次并关闭，再复查端点表（应变为 `0x01 0x81 0x82 0x06`，alt=0） |
| 设备未初始化 | 冷插上、从未跑过原厂软件；数据端点不存在，或枚举不到设备 | 启动原厂软件，等识别到设备后关闭；若枚举不到，检查 USB 线与 WinUSB 驱动 |
| 固件挂起 | 枚举正常但所有端点读写都报 121 超时 | 主机侧无法复位，只能物理拔掉 USB 线、等 5 秒、插回，再跑一次原厂软件 |

额外提醒：明文写入"成功"（返回写入字节数）**不代表**设备接受。判断协议是否正确，唯一可靠的依据是设备是否真的吐出数据。
