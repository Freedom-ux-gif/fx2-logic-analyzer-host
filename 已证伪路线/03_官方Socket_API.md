# 官方 Socket API —— 只收不回的旁路

> 状态：已放弃（服务端实现完整但被禁用；理论上可行，但属本项目主动放弃的范围）

## 试了什么

既然 USB 协议难啃，转向原厂软件**自带的 TCP Socket API**：纯 Python 标准库 + frida，绕开 USB 逆向，走"文档化"的官方接口。

- 端口 **10429**，由 frida `bind` 事件实测确认，且原厂日志出现 `New Socket Connection, port: 10429`；监听 backlog 实测为 50，接受连接走 `WSAAccept` 而非 `accept`。
- 开启方式：修改 `settings.xml` 把 `mEnableSocketServer` 从 0 改成 1（改前备份、且必须在 Logic.exe 未运行时改）。关闭时再改回。
- 客户端做了完整自检：启动 → 连接 → 发命令 → 断开 → 清理；探测了 46 条命令中的若干条（`GET_CONNECTED_DEVICES`、`GET_SAMPLE_RATE`、`CAPTURE`、`BOGUS_CMD` 等）以及请求格式（换行结尾 / CRLF / 无结尾、大小写敏感性）。
- 用 frida 抓 socket 明文，并配套 `trigger_full.py`：用完整 14 函数 USB 钩子记录发 `CAPTURE` 命令后原厂到底对设备做了什么。

## 观察到什么

- **服务端只收不回**：frida 抓到 **702 个事件**，服务端通过 WSARecv 确实收到了客户端发的命令文本，但 Winsock 层（send / WSASend）**零事件、0 字节发出**。客户端 recv 超时或收到连接重置（WinError 10054）。命令 `GET_CONNECTED_DEVICES`、`GET_SAMPLE_RATE`、`CAPTURE` 乃至错误命令 `BOGUS_CMD` 全部无响应——连错误应答都没有。
- **无法区分"服务端不识别"与"服务端没启用应答"**：小写命令发出后无响应，既可能是大小写敏感、也可能是服务端根本没在回。没有响应样本，就无法判断任何参数格式、应答分隔或长度前缀。
- **`CAPTURE` 不触发 USB 写**：发 `CAPTURE` 命令后，完整 USB 钩子里没有出现任何新的设备写入——该命令被**静默忽略**，没有让原厂进入采集态。（早期用最小 3 函数钩子误以为"无写入"，换成完整钩子后确认结论不变，见 `04_触发与GUI自动化.md`。）
- 对比 USB 路线的优缺点很清楚：优点是官方支持、不碰设备协议/WinUSB 句柄、不与其他执行手争抢设备；缺点是必须先运行 Logic.exe、必须改配置文件才能开启服务端、且实测不接受命令应答，拿不到采集结果。
- 服务端实现看起来**完整**（命令表 46 条、有监听/接受逻辑），只是被禁用或没接上采集链路——这是"可惜"而非"不存在"的失败。

### 实测命令与应答一览

| 发送 | 参数格式 | 实测应答 |
|---|---|---|
| `GET_CONNECTED_DEVICES`（换行/CRLF/无结尾三种） | 空格分隔文本 | 全部空 |
| `GET_SAMPLE_RATE` | 同上 | 空 |
| `CAPTURE` | 同上 | 空，且不触发 USB 写 |
| `get_connected_devices`（小写） | 同上 | 空（大小写敏感性无法判断） |
| `BOGUS_CMD`（错误命令） | 文本 | 空（连错误应答都没有） |

三种行尾格式（换行、CRLF、无结尾）都被服务端 WSARecv 收到，说明请求格式本身不是问题；问题在服务端不出应答。这个"全空"的整齐结果反而很有说服力：它排除了"某一格式碰巧不对"的可能，把矛头直接指向服务端实现/开关。

另一个值得记录的细节：`subprocess.Popen` 独立启动的 Logic.exe 在本环境连接常超时，而 frida `spawn` + attach + resume 启动的能连上（仍需重试）。原因疑似设备被另一执行手占用导致初始化时序不同，未下定论——它说明 socket 这条路的稳定性还受设备独占状态影响，不能把"连不上"一律归因于协议，也不能把"偶尔连上"当成服务端可用的证据。

## 结论

- 这条路理论上可行：服务端代码在原厂软件里是完整的，只是被开关关掉了。若能找到**启用条件**（除了 `mEnableSocketServer` 之外是否还有别的开关/初始化时序）或打补丁把它接上采集链路，它仍可能成为绕开 USB 逆向的捷径。
- **但本项目主动放弃**：这条路需要**修改原厂软件**——无论是改配置绕过开关还是二进制补丁，都超出互操作性研究的边界（我们的目标是理解协议，不是篡改原厂程序）。**本项目不提供补丁。**
- 明确写在这里，避免后来者误解：**这条路理论上可行，但属于本项目主动放弃的范围——它需要修改原厂软件，超出互操作性研究的边界。**
- "只收不回"还有一层教训：如果没有 frida 抓到那 702 个事件，单看客户端超时会误以为是网络/参数问题；抓包证据把问题准确定位到服务端不出应答，让"放弃"成为有依据的决定而非猜测。

## 若要再试，需要什么

- 找到 `mEnableSocketServer` 之外的启用条件，或证明服务端应答走的是 Qt5Network 内部实现（未经 `ws2_32` 导出表），需要更深的 frida hook 点——但这两条都涉及对原厂软件的深入修改/干预，本项目不做。
- 若要验证"socket 能否控制采集"，可换用能正常应答服务端的原厂版本/环境复测；但需注意不同版本命令集可能不同，结论不可直接外推。
- 如果只是想拿到采集数据，别走 socket——走 USB 协议状态机这条路更接近问题核心，也是在研究边界内的正途。
- 补充一点范围界定：46 条命令的完整命令名表来自镜像实读，本目录只记录实测验证过的少数几条；未实测的命令参数、应答词（如 `Success`、`Could not understand command...`）均不作为结论，只在镜像字符串里见过。

**教训：** "官方支持"不等于"对我们开放"。一个被禁用的完整实现，比一个不存在的功能更诱人，也更容易耗掉时间；认清研究边界，才不会被"就差一点"的错觉拖住。
