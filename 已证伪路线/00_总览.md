# 已证伪路线 —— 我们走过、并确认走不通的路

> 状态：部分可行（四条路线中两条彻底证伪、一条主动放弃、一条部分可行但手段本身有局限）

> 本目录记录的是走不通的路。列出它们的目的不是失败展览，而是让别人不必重复付出同样的成本。

> 说明：本目录只保留**结论**。原始日志（jsonl）、探测脚本（py）、抓包二进制（bin）均不随副本分发；
> 每条路线的事实依据来自原始工程，此处只做压缩与归纳，不复现原始材料。
>
> **下文中出现的 `02_usb` / `04_protocol` / `05_socket` / `07_trigger` 等写法，指的是原作者本地工程里的目录名，本仓库不包含它们。** 保留这些名字是为了让叙述有出处可循；相关结论已全部写进本目录的五个文件。

## 试了什么

四个目录、约 14 MB 的日志与探测代码，代表四条曾经认真投入的方向：

- **02_usb**：用 frida 在原厂进程内 hook WinUSB 调用，想直接抓出协议。
- **04_protocol**：在确认握手后，枚举短命令字节，想撞出"启动采集"命令。
- **05_socket**：转向原厂自带的 TCP Socket API，想绕开 USB 逆向。
- **07_trigger**：尝试触发一次真实采集（GUI 按键 / socket 命令），并调研硬件触发寄存器。

这四条路线都曾被认为是"最有希望 breakthroughs"的方向；把它们集中起来评估，才能看清整体成本。

## 观察到什么

| 路线 | 尝试的成本 | 结论 | 还值得再试吗 |
|---|---|---|---|
| frida hook WinUSB 抓包（02_usb） | 一套约 14 函数钩子 + 数小时调试；产出约 7.6 MB jsonl | 抓到完整调用轨迹，确认原厂走 WinUSB 而非私有驱动；但只能看调用、看不到设备内部 | 手段可复用（插上设备即可抓真实采样），但日志本身无阅读价值，不必再投入 |
| 命令字节盲猜（04_protocol） | 113 种短写命令逐条实测 + 多组采样率交叉验证 | 全部超时（错误 121）；问题不在字节，而在握手后缺一个未知状态转移 | 不值得。必须先从反汇编/抓包拿到命令格式，再谈枚举 |
| 官方 Socket API（05_socket） | 改配置 + frida 抓 702 个事件 + 客户端多轮试探 | 服务端实现完整但被禁用：只收不回（0 字节发出），`CAPTURE` 不触发 USB 写 | 理论上可行，但需修改原厂软件或找到启用条件，属本项目主动放弃范围 |
| 触发与 GUI 自动化（07_trigger） | GUI 按键注入 + 硬件触发寄存器调研 + 应答性质实验 | GUI 控件无独立 HWND、按键送不进；硬件触发是物理限制，彻底不可行 | 硬件触发不要试；软件触发已落地，见 `12_trigger/` |

汇总起来，四条路线的失败原因并不相同：第一条是**手段能力边界**（看得见调用、看不见状态），第二条是**问题定位错误**（盲猜掩盖了真正的状态转移缺失），第三条是**主动的范围放弃**（需要改原厂软件），第四条是**物理限制**（FX2 无硬件触发能力）。把它们混为一谈会得出"我们不行"的错误结论；分开看，每一条都有清晰、可复用的教训。

## 结论

- **证伪比证实更重要——本项目最大的节省，来自及早确认哪些路不用走。** 一条被明确否定的路，比十条模糊的"也许可以"更值钱。
- **「写入成功」≠「协议正确」。** 设备可以正常应答你的写命令，却始终不出数据；把"命令被接受"当成"方向对了"，会浪费大量时间在错误假设上。这是本项目最大的认知转折点（详见 `02_命令盲猜.md`）。
- 抓包给的是**证据**，开源文档给的是**假设**，反汇编给的是实现细节；三者对撞一致才升级为结论，不一致就如实保留，不编造。
- 真正有价值的产出不是"采到了数据"，而是排除了四条死路后，把资源集中到软件触发与协议状态机这两条仍有希望的路径上。

### 四条路线之间的关系

四条路线不是并列的四次尝试，而是一条递进的因果链，理解这一点比记住各自结论更重要：

1. **抓包（01）** 提供了协议线索，也暴露了"自动化环境里没有真实采集"这一根本盲点。
2. 为了补上这个盲点，先试 **GUI 自动化与 socket 触发（04）**，结果两条都送不进/不触发。
3. 采不到真实采集段，就只能靠 **命令盲猜（02）** 去撞启动命令，撞了 113 种全部超时——这才定位到问题不在字节，而在未知状态转移。
4. 转而想绕开 USB 的 **Socket API（03）**，发现服务端被禁用且只收不回，只能放弃。

换句话说：每一条路都是上一条失败后自然冒出的"下一步"，而不是四个独立的灵感。把它们按顺序读，能看清项目是怎么一步步收敛到"软件触发 + 协议状态机"这个正确焦点上的。

### 给接手者的最短读法

- 只有半小时：读本页总表 + `02_命令盲猜.md` 的教训段。
- 想看具体证据来源：原始素材在原作者的本地工程里（`04_protocol/commands.md` 第 6 节），**该目录未随本仓库分发**；本页与 `02_命令盲猜.md` 已把它整理成结论。方法论见 `交接手册/H3_逆向方法.md` 第 4 章。
- 想继续推进采集：不要再枚举命令字节；先解决"握手后缺一个状态转移"这个真正的未解项。

## 若要再试，需要什么

- 判断"什么时候该放弃一条路"的标准，见 `交接手册/H3_逆向方法.md` 第 4 章「证伪清单」与第 5.4 节。
- H3 第 4 章逐行标注了"已付出的成本"与"若要再试需要什么"；接手时先读它，再决定要不要重走。
- 通用放弃信号：反复只得到"无响应 / 无数据 / 固定应答"，而继续尝试需要突破安全边界、修改原厂软件、或依赖不存在的硬件能力——此时应止损转向。
- 分路线结论索引：`01_frida_USB抓包.md`、`02_命令盲猜.md`、`03_官方Socket_API.md`、`04_触发与GUI自动化.md`。

**教训：** 四条路各自花掉的小时数，换来一张清晰的"此路不通"地图；把它写下来比把日志堆在仓库里更有价值。后来者读这五份结论，就应该能忍住不重走同样的路。
