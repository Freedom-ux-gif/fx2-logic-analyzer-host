# 触发与 GUI 自动化 —— 送不进的按键，不存在的寄存器

> 状态：已证伪（GUI 自动化送不进按键；硬件触发是物理限制，彻底不可行；软件触发已另行落地）

## 试了什么

为了拿到"真实采集"那一段 USB 流量（空闲抓包一直缺的就是它），原作者做了两组尝试，另配套一组协议性质实验；硬件触发的可行性则来自一手资料调研。下面提到的脚本名（`gui_trigger.py` 等）**均未随本仓库分发**，保留名称只为说明当时的做法。

- **GUI 自动化触发采集（`gui_trigger.py`）**：spawn `Logic.exe` 并挂上完整 USB 钩子，等窗口出现后把它置前、发送"开始采集"快捷键（`ctrl+enter`），记录随后所有 WinUSB 传输。想法是让原厂软件自己点开始，就能抓到采集序列。
- **socket 命令触发采集（`trigger_full.py`）**：既然 socket 有 `CAPTURE` 命令，尝试用它代替人工点击；配套使用完整 14 函数 USB 钩子，修正了早期最小 3 函数钩子"看到零写入"的误判。
- **应答性质实验（`distinguish.py`）**：四组实验判断那 8 字节读是"命令-应答对"还是"设备独立数据流"——读前不写、写假命令后读、换 divider 看 8 字节是否变化、写两次读一次。这决定了"存在加密握手"的前提是否成立。
- **硬件触发调研（结论见 `14_research/R6_trigger_analog.md`）**：查 sigrok wiki、fx2lafw 设备表、`soft-trigger.c` 源码与本机实测事实，判断这块 0925:3881 八通道纯数字克隆板能不能做硬件触发。

## 观察到什么

- **GUI 自动化：按键送不进。** Qt 控件没有独立 HWND，找不到可定位的子窗口；`SetForegroundWindow` 被系统拒绝，窗口抢不到前台；`keybd_event` 发出去也没有落到目标控件上。结果是 `gui_trigger.py` 没能触发一次真实采集——自动化环境里那"唯一缺的一次点击"始终补不上。
- **socket 触发：`CAPTURE` 静默忽略。** 即便用完整 USB 钩子，发完 `CAPTURE` 也没有任何新的设备写入，服务端 0 字节发出（详见 `03_官方Socket_API.md`）。这条路同样没能进入采样态。
- **应答性质实验**：指向 8 字节读是对 5 字节配置的固定应答（每次一致、非随机挑战），设备并没有在独立流式吐数据——"加密握手/动态认证"的前提不成立，问题仍回到"握手后缺一个状态转移"。
- **硬件触发：三层证据一致否定。** 协议层——我们只逆出"设采样率 + 启动采集"命令，**未找到任何触发寄存器协议**，没有下发触发条件的通道；固件层——sigrok 对原版 Logic 的触发标注是 `none (SW-only)`，`soft-trigger.c` 在**主机侧**对流式数据逐样本匹配，预触发环形缓冲在主机内存里、深度由内存决定；硬件层——FX2 芯片没有逻辑触发外设，内部 FIFO 仅 **4×512 字节**量级，克隆板无板载大容量缓存，即便固件支持触发，预触发深度也浅得没有意义。

### 硬件触发三层证据展开

| 层级 | 关键事实 | 来源 |
|---|---|---|
| 协议层 | 只逆出设采样率 + 启动采集两条命令；触发类型/通道掩码/边沿条件/预触发深度寄存器**均未逆出** | 本机实测（协议还原） |
| 固件层 | sigrok 将原版 Logic 标注 `none (SW-only)`；`soft-trigger.c` 用 `SR_TRIGGER_ZERO/ONE/RISING/FALLING/EDGE` 在主机侧逐样本匹配，多级 stage 推进，命中后回放预触发环形缓冲 | sigrok wiki / GitHub 源码一手证据 |
| 硬件层 | FX2（CY7C68013A）无逻辑触发外设；内部 FIFO 仅 4×512 字节量级；克隆板多为 74HC245/244 缓冲器而非 RAM，无板载大容量缓存 | fx2lafw 设备表 / R6 调研 |

三层证据互相印证：即便协议层将来逆出触发命令，固件层与硬件层也决定了"硬件触发"在这块板上没有意义——触发条件的匹配与预触发存储都只能发生在**主机侧**，这就是软件触发的定义。

### 为什么软件触发是唯一可行路径

- 设备侧全量上送原始数据，主机侧用环形缓冲保存最近 N 个样本（预触发），逐样本匹配触发条件，命中后回放缓冲并继续采集（触发后数据）。
- 预触发深度由主机内存决定（`unitsize × pre_trigger_samples`），想设多大设多大（受内存限制），正好绕开 FX2 FIFO 极浅的物理限制。
- 这条路径与 sigrok `soft-trigger.c` 的实现思路一致，不依赖任何未逆出的寄存器，也不需要修改原厂软件——是边界内唯一能落地的触发方案。

## 结论

- **GUI 自动化这条路走不通**：Qt 自绘控件不暴露 HWND，Win32 按键注入够不着它；若要再试，需要 UI Automation / 无障碍接口（如 MSAA、UIA）而非 `keybd_event`，或直接放弃 GUI、走 USB 层解决状态转移问题。
- **硬件触发彻底不可行**：这是物理/架构限制，不是"还没逆出来"。协议、固件、硬件三层证据一致——没有触发寄存器、sigrok 走软件触发、FX2 FIFO 极浅。**不要浪费时间。**
- 因此本项目采用**软件触发**路径：**先采全量到内存、离线找触发点、保留预触发**——这与 sigrok `soft-trigger.c` 的环形缓冲思路一致，也是这块板唯一可行的方式。
- 明确写在这里，避免误解：**软件触发已经实现，见 `12_trigger/`。硬件触发是物理限制，不要浪费时间。**

## 若要再试，需要什么

- GUI 自动化若要再试：改用 UI Automation / 无障碍接口定位并操作 Qt 控件；但这只是为了解决"抓到真实采集流量"这一手段问题，优先级低于直接攻克协议状态转移。
- 硬件触发若要再试（**当前不建议**）：需逆出触发类型寄存器、通道掩码、边沿条件、预触发深度寄存器的字节格式与混淆算法，用 USB 抓包对比"设置触发前后"的控制传输，并验证克隆固件是否真的实现了这些寄存器——任一步失败即回到软件触发。鉴于工作量大、收益不确定，建议不投入。
- 当前真正该做的：解决 `02_命令盲猜.md` 指出的"握手后状态转移缺失"——不需要新硬件，也不需要改原厂软件。

### 一个容易混淆的点

`distinguish.py` 的四组实验里，"写两次读一次"尤其关键：若 8 字节是命令-应答对，第二次写的应答应继续排队等待读取；若是独立数据流，则两次写与读之间没有对应关系。这类实验的价值在于——它用极低成本把"是否存在加密认证芯片"这个诱人但错误的假设提前关死，避免团队沿着"破解动态挑战"这条不存在的路继续投入。它和硬件触发调研是同一种工作：**先花小成本证伪，再决定是否投入大成本**。

### 与总览的呼应

本文件对应总览表中的"触发与 GUI 自动化"一行，也对应 H3 证伪清单中的"GUI 自动化触发采集"一行。两条不同路径（GUI 注入与 socket 命令）在同一件事上失败——都没能让原厂进入真实采样态——恰好互为佐证：问题不在我们用哪种方式点击"开始"，而在上位机协议层那个尚未找到的状态转移。

两条路径失败的方式还各有启发：GUI 那条卡在"控件不可寻址"（Win32 API 层面的障碍），socket 那条卡在"服务端不回"（原厂实现层面的障碍）。障碍不在同一层，却指向同一个缺口，这比单一路径失败更有说服力——它说明"缺一次真实采集"不是工具选得不对，而是我们对设备状态机的理解还差最后一块。

**教训：** 有些"不行"是方法没选对（GUI 注入该用 UIA），有些"不行"是物理规律（FX2 没有硬件触发）。分清这两类，才能把时间花在真正有解的那一类上。
