# frida USB 抓包 —— 看清了调用，看不清设备

> 状态：部分可行（手段本身可用，但它回答的问题有限，且原始日志未随仓库分发）

## 试了什么

在 `Logic.exe` 进程内用 frida 挂钩 WinUSB 相关 API，目标是抓到原厂软件对设备的完整控制传输 / 批量传输参数与收发数据，为自研上位机提供协议依据。

- 挂了 `CreateFile`（设备句柄打开）、`DeviceIoControl`（设备 IOCTL）、`WinUsb_*` 系列（控制传输、批量读写、管道策略）等一整套约 14 个函数。
- 提供了三种用法：免交互自检（启动 12 秒自动退出）、attach 到已打开的进程、自行启动并抓取直到手动中断。三种用法共用同一套钩子与日志格式。
- 日志按 JSONL 逐行记录，公共字段含毫秒时间戳、线程 ID 与墙钟时间；事件类型覆盖句柄打开与返回、ReadFile/WriteFile、IOCTL、WinUsb 控制传输/读写/管道策略、dll 加载、钩子就绪与异常计数。
- 设计意图很明确：既然原厂软件能与设备通信，那么把它对设备说的一切都录下来，协议自然浮现——这是最朴素也最值得先试的一条路。

## 观察到什么

- 本机未插设备时只能抓到 SetupAPI 的枚举调用（`SetupDiGetClassDevsA` 一类）——**这不代表钩子失效**，只是没有真实设备流量。插上设备后相关钩子才会出真实数据；"当前日志没有采样数据"与"脚本没生效"是两回事。
- 抓到的核心事实：原厂软件通过 **WinUSB** 驱动栈与设备通信，走标准 `winusb.dll` 导出，**不是私有内核驱动**。这一点由 `winusb.dll` 被加载、`WinUsb_*` 事件成批出现直接证实——它回答了一个之前只能靠猜的问题。
- 还观察到握手阶段的完整形状：官方对多条管道设置管道策略（超时、忽略短包、RAW_IO 等），用 `WritePipe` 下发短命令、用 `ReadPipe` 读回应答。这些正是后续协议还原（`61 <divider>` 设采样率、5 字节固定挑战-应答）的原始依据，也验证了抓包"拿来当协议线索"的价值。
- 局限一：只能看到**主机侧调用了什么**（参数、句柄、时序、字节流），看不到设备内部状态机。"设备收到命令后为什么不吐数据"这类问题，抓包本身回答不了——它记录了对话，却不理解对话。
- 局限二：日志体积巨大（约 **7.6 MB jsonl**），绝大多数是重复的枚举态事件，真正有信息量的握手只有寥寥数条。**原始日志本身未随仓库分发**——留下的是从它里面提炼出的结论，不是日志文件本身。
- 局限三：自动化环境里没人点"开始采集"，60 秒长日志只有连接与握手两条写命令，全是空闲态。抓到的越多，越容易误以为"协议已经到手"，其实关键的启动采集段根本没被录进去。

## 结论

- 作为"确认通信栈"的手段，这次抓包是成功的：它把"原厂用什么驱动"从猜测变成事实（WinUSB），并提供了协议还原所需的握手字节。
- 作为"直接拿到协议答案"的手段，它是失败的：数据管道、启动采集命令、触发配置都没有因为抓包而自动浮现——因为自动化环境里缺少一次真实采集，抓包钩子始终处于"就绪态"而非"采样态"。
- 因此抓包常被误当成终点，实际只是起点：**它告诉你对设备说了什么，不告诉你设备为什么不回应**。把 7.6 MB 日志当成成果囤积，是这条路线最典型的误区。

## 若要再试，需要什么

- 设备真正插上、且由自动化触发一次**真实采集**（而不是空闲握手），钩子的就绪态才会产出有采样数据的日志。原作者当时分别用 GUI 自动化与 socket 命令两种方式尝试触发（见 `04_触发与GUI自动化.md`），结论是两条都未能让原厂进入采样态。
- 日志中最有价值的四类事件（值得保留的协议线索）与最没价值的三类（可安全丢弃）大致如下，供后来者裁剪日志时参考：

  | 价值 | 事件类型 | 用途 |
  |---|---|---|
  | 高 | `createFile` / `createFileRet`、`winusbLoaded` | 确认设备句柄与驱动栈（WinUSB） |
  | 高 | `ioctl`、`winusbControl` | 控制传输参数、握手短命令 |
  | 高 | `winusbWrite` / `winusbRead`、`winusbPipePolicy` | 批量数据流与管道配置 |
  | 低 | 大量重复的 SetupAPI 枚举调用 | 空闲态噪声，无阅读价值 |
  | 低 | `ready` / `miss` / `err` | 仅用于确认钩子自身健康 |

- 若只关心"设采样率 / 握手序列"，现有结论已足够，无需重抓；原始 7.6 MB 日志未提供，也不必索取——它没有再被阅读的价值。
- 想进一步看设备内部状态，只能从固件/反汇编入手：抓包这条路到此为止，继续堆日志不会带来新信息。
- 一个具体的踩坑值得记住：早期用**最小 3 函数钩子**抓 socket 触发过程时读到零写入，差点得出"socket 命令无效"的错误结论；后来换成 02_usb 那套完整 14 函数钩子才看清——Logic 走的是那三个函数覆盖不到的初始化路径（详见 `04_触发与GUI自动化.md`）。**钩子不全时，"没抓到"不等于"没发生"。**
- 同理，未插设备时日志里"什么都没有"也不能当成"协议不存在"——钩子的就绪态与采样态是两回事，读懂日志前先确认设备与触发条件是否到位。
- 如果要复用这套钩子做新实验，建议保留"钩子健康"事件（`ready`/`miss`/`err`）作为自检基线：它们为零时，才能把"没抓到数据"归因为设备行为而非工具故障。
- 这条经验直接影响了后续实验的设计：`trigger_full.py` 与 `gui_trigger.py` 都改用完整的 14 函数钩子，而非重新推导最小集合——这正是从本次抓包踩坑里学到的。
- 一句话概括这次抓包的定位：**它证明了 WinUSB 通信栈，却没有证明任何一条协议命令**——把这两件事分开，才不会高估成果。

**教训：** 抓包是把"看不见"变成"看得见"的放大镜，但放大的是调用，不是意图。先把要问的问题想清楚再抓，否则只会收获一堆没有阅读价值的 MB。
