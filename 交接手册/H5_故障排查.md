# H5 故障排查

> 面向「出问题就抓瞎」的人。按你**看到的现象**查，不要按原因猜。
> 目标：从症状出发，5 分钟内定位原因并解决。
> 最后更新：2026-11-25

---

## 0. 先做这三件事

不管什么症状，先跑这三条。它们覆盖了 80% 的情况。

**① 设备在系统里吗？**
```bash
powershell -NoProfile -Command "Get-PnpDevice -PresentOnly | Where-Object {$_.InstanceId -match '0925'} | Format-Table Status,FriendlyName"
```
预期：`Status=OK`。如果列表是空的 → 线没插好 / 驱动没装 / 设备已断开（见 5.1）。

**② 后端服务活着吗？**
```bash
curl -s http://127.0.0.1:8421/api/status
```
预期：返回一段 JSON，含 `"ok":true`、`device`、`rates`。连不上 → 服务没起或端口变了（见 1.2、3.6）。

**③ 页面样式加载了吗？**
浏览器打开 `http://127.0.0.1:8421/`，按 F12 → Network 标签 → 刷新。
预期：`style.css` 和 `app.js` 都是 `200`。若 `style.css` 是 `404` → 见 1.3。

> 端口不一定是 8421：启动器从 8421 起找第一个空闲端口，实际端口看黑框里打印的「实际端口：xxxx」。

## 1. 按症状查（17 条）

### 1.1 双击 exe 没反应 / 黑框一闪就没了

- **现象**（用户原话）：「双击 LogicWeb.exe 啥也没发生」「黑框闪一下就关了，页面也没开」。
- **可能原因**（按概率）：
  1. 打包时用了 `--noconsole`，`sys.stdout` 是 `None`，启动时 `sys.stdout.reconfigure()` 抛 `AttributeError: 'NoneType' object has no attribute 'reconfigure'` 直接退出。
  2. `python -I` 清空了 CWD 和 `PYTHONPATH`，脚本里没写 `sys.path.insert(0, ...)`，找不到 `server` 等模块。
  3. 端口全被占（8421~8430 都被占），抛 `RuntimeError: 8421 到 8430 端口都被占用`。
- **验证方法**：
  ```bash
  cd 13_web
  python -I launcher.py
  ```
  直接在黑框里跑，看完整报错。若报 `AttributeError ... reconfigure` → 原因 1；若报 `No module named 'server'` → 原因 2。
- **解决方法**：
  - 原因 1：打开 `13_web/launcher.py`，确认第 107 行是 `if hasattr(sys.stdout, "reconfigure"):` 再调 reconfigure；`03_host/winusb.py` 第 24 行同理。没有这两层判断就补上。
  - 原因 2：打开 `13_web/launcher.py`，在 `import server` 之前加 `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))`；`start.bat` 里保持 `python -I launcher.py %*` 的写法不要改成 `python launcher.py`。
  - 原因 3：关掉占用端口的旧进程（见 5.3），或 `python -I launcher.py --port 8500` 指定新端口。

### 1.2 浏览器没自动打开

- **现象**：「黑框显示服务启动了，但浏览器没弹出来」「得自己手输网址」。
- **可能原因**：
  1. 启动器开了 `--no-browser` 或环境变量禁用了浏览器（launcher 只在非该选项下调 `webbrowser.open`）。
  2. 系统默认浏览器没设置 / 关联坏了，`webbrowser.open()` 静默失败。
  3. 黑框其实没启动成功，只是用户没往下翻看到报错。
- **验证方法**：看黑框输出的 `实际端口：xxxx`，手动在浏览器打开 `http://127.0.0.1:xxxx/`。能打开 → 只是自动打开失败；打不开 → 服务没起，按 1.1 查。
- **解决方法**：
  - 手动打开 `http://127.0.0.1:8421/`（端口以黑框实际打印为准），把网址存成书签，不必纠结自动弹窗。
  - 要修自动打开：打开 `13_web/launcher.py` 第 134~135 行，确认 `threading.Timer(0.6, lambda: webbrowser.open(url)).start()` 存在；在 Windows 设置 → 应用 → 默认应用 → Web 浏览器里指定 Edge/Chrome。

### 1.3 页面打开但白屏 / 整页无样式

- **现象**：「页面出来了但没颜色没排版，像纯 HTML」「一片空白啥都没有」。
- **可能原因**（按概率）：
  1. `index.html` 里写了相对路径 `style.css`，页面在 `/` 下，浏览器请求 `/style.css` 得到 `404`（正确应写 `/static/style.css`）。
  2. 前端 JS 有运行时错误，如 `buildExportBar is not a function` —— 只写了调用没写方法体，语法合法、运行时才崩，导致白屏。
  3. 时间轴绘制崩溃（见 1.13）连带整个渲染中断。
- **验证方法**：按 F12 → Console 标签，看红字。若报 `Uncaught TypeError: ... is not a function` → 原因 2；切到 Network 看 `style.css` 状态码，`404` → 原因 1。
- **解决方法**：
  - 原因 1：打开 `13_web/static/index.html`，把第 7 行改成 `<link rel="stylesheet" href="/static/style.css">`，第 146 行改成 `<script src="/static/app.js"></script>`。
  - 原因 2：打开 `13_web/static/app.js`，在 `App` 对象里补上 `buildExportBar: function () { ... }` 方法体（现状第 1054 行已有，缺的是它被调用的早期版本）。
  - 原因 3：见 1.13。

### 1.4 徽章显示「设备未就绪」

- **现象**：「右上角显示红点『设备未就绪』，点采集没反应」「banner 说请先启动一次 Logic.exe」。
- **可能原因**（按概率）：
  1. **alt setting 错**：alt 0 没有端点，所有 pipe 操作返回 `ERROR_INVALID_PARAMETER(87)` —— 这个坑当年被误判成「设备坏了要拔插」，实际不用拔插。
  2. **设备未初始化**：冷启动后采集引擎没配置，缺 `0x82` 端点，需要官方软件先跑一次。
  3. 明文命令写进去了但设备不吐数据（必须加密），后端判定未就绪。
- **验证方法**：跑端点枚举（见 3.2）看 `alt` 与端点表 —— **实测结论（2026-11-25 复核）**：**未初始化**状态为 `alt=1`、6 端点表（`0x01 0x81 0x02 0x04 0x86 0x88`），此时无 `0x82`、采不到数据；经原厂软件初始化后为 `alt=0`、4 端点表（`0x01 0x81 0x82 0x06`），数据端点即 `0x82`。 也可跑 `python -I launcher.py` 看 `--self-check` 的 `device` 字段（`initialized` 是不是 false）。
- **解决方法**：
  - 原因 1：确认 `03_host/winusb.py::_select_endpoint_alt_setting` 被调用切到 alt 1（alt 1 才有 6 个端点）。**不要拔插设备**。
  - 原因 2：**先双击运行一次 Logic.exe（或 LogicScope.exe），等它初始化完再关闭**，然后点页面 banner 的刷新。注意：设备还被占用时先关掉程序再刷新。
  - 原因 3：确认命令用加密形式 `d5 8e` 而不是明文 `01 2f`（见 1.7）。

### 1.5 徽章显示「设备被占用」

- **现象**：「黄点『设备被占用』」「banner 说请关闭 LogicScope.exe / Logic.exe」。
- **可能原因**：
  1. 之前双击的 `LogicScope.exe` / `Logic.exe` 忘了关，攥着设备句柄。
  2. 另一个自己的采集进程（`capture_fx2.py`）还在跑。
- **验证方法**：任务管理器（Ctrl+Shift+Esc）→ 详细信息，搜 `LogicScope.exe`、`Logic.exe`、`python.exe`。
- **解决方法**：
  - 在任务管理器里结束 `LogicScope.exe` 和 `Logic.exe` 进程，然后点 banner 上的「点击此处刷新」。**不用拔 USB 线**。
  - 若是自己的 python 进程，`taskkill /F /IM python.exe` 后重试（注意会杀掉别的 python 任务）。

### 1.6 点【开始采集】没反应（按钮灰的）

- **现象**：「开始采集按钮是灰的，点不动」。
- **可能原因**（按概率）：
  1. 后端未连接（`refreshStatus()` 把徽章设成 `● 后端未连接` 并 `setCaptureEnabled(false)`）。
  2. 设备未就绪 / 被占用（见 1.4、1.5），按钮被禁用。
  3. 上一轮采集还在进行（`busy=true`），按钮临时禁用。
  4. **采样率选不上**：`refreshStatus()` 每 5 秒重建 `<select>`，把用户选的值冲掉（实测设 24MHz 又跳回 1MHz），以为没选上其实是选了又被重置。
- **验证方法**：F12 → Console 看有无报错；看徽章文字判断是 1/2/3 哪种；选一个采样率后盯 5 秒看是否跳回。
- **解决方法**：
  - 原因 1/2：按 1.4、1.5 处理，徽章变绿后按钮自动可用。
  - 原因 3：点【停止】或等当前采集完成（后端返回「设备正在采集中，请等待当前采集完成」）。
  - 原因 4：打开 `13_web/static/app.js` 第 931~943 行，确认只有选项签名 `data-sig` 变化时才重建 `<select>`（现状已修），不要无条件 `sel.innerHTML=''`。

### 1.7 采集到 0 字节

- **现象**：「采集完了，数据大小 0 字节」「提示『没有收到采样数据』」。
- **可能原因**（按概率）：
  1. **命令没加密**：明文 `01 2f` 写入成功但设备返回 0 字节；加密 `d5 8e` 才返回 1.5 MB。
  2. **数据在错误端点**：`0x81` 只回 1 字节 ack；数据端点由初始化状态决定 —— **实测结论（2026-11-25 复核）**：**未初始化**状态为 `alt=1`、6 端点表（`0x01 0x81 0x02 0x04 0x86 0x88`），此时无 `0x82`、采不到数据；经原厂软件初始化后为 `alt=0`、4 端点表（`0x01 0x81 0x82 0x06`），数据端点即 `0x82`。
  3. alt setting 错（87）或未初始化（121），根本没开始流。
- **验证方法**：
  ```bash
  cd 08_fx2
  python -I capture_fx2.py --rate 1000000 --seconds 3 --probe
  ```
  `--probe` 会逐个端点试，看哪个端点吐数据。明文/加密对比：写 `01 2f` 记字节数，再写 `d5 8e` 记字节数。
- **解决方法**：
  - 原因 1：改用加密命令 `d5 8e`，不要用明文 `01 2f`。
  - 原因 2：先确认设备已由原厂软件初始化（初始化后数据端点就是 `0x82`，无需改代码）；若枚举仍是 `alt=1` 的 6 端点表，说明未初始化，去跑一次 Logic.exe。**以你自己 `list_pipes()` 的输出为准**，不要照搬旧文档的 `0x88` 说法。
  - 原因 3：按 1.4 处理 alt setting 和初始化。

### 1.8 采集到的数据量远少于预期 / 达成率不是 100%

- **现象**：「设了 8MHz 采 3 秒，文件小得离谱」「界面显示达成率 84.8%」。
- **可能原因**（按概率）：
  1. **单线程丢 99% 数据**：同步 `read_pipe` 两次调用之间的间隙让 FIFO 溢出，8MHz 单读线程只有 0.5% 成功率。必须 2~3 个并发读线程。
  2. **达成率分母算错**：分母用了含线程启动开销的 `elapsed`，分子已被裁剪到精确长度，显示 84.8%；改用 `seconds` 后显示 100%。
  3. 采样率被 5 秒刷新冲掉（见 1.6 原因 4），实际用了低采样率。
- **验证方法**：看文件大小 ≈ `采样率 × 秒数 × 字节/样本`？远小于即中招；看界面达成率字段。
- **解决方法**：
  - 原因 1：把采集读线程从 1 个改成 2~3 个并发读（`capture_fx2.py` / `capture_verified.py`），不要单线程同步读。
  - 原因 2：打开后端达成率计算处，把分母从 `elapsed`（含启动开销）改成用户设定的 `seconds`。
  - 原因 3：按 1.6 原因 4 修复 `<select>` 重建逻辑。

### 1.9 波形全是一条直线 / 通道看着恒高恒低

- **现象**：「波形是条直线」「通道一直是高电平」。
- **可能原因**（按概率）：
  1. **通道映射搞反**：sigrok 文档说 CH1=bit7，实际本板 CH0=bit0；接 CH0 采到 `0xFE/0xFF`（只有 bit0 在变），代码按 CH1 去读就是恒高。
  2. 信号线没接 / 接错通道 / 信号源没开输出。
  3. **恒定通道显示误导**：原本显示「脉宽 1 秒」，实际是整段电平不变，不是真的有 1 秒脉宽。
- **验证方法**：用一个已知 1kHz 方波接 CH0，采 1 秒，看 CH0 有没有跳变；F12 看 banner 是否提示「未检测到信号跳变」。
- **解决方法**：
  - 原因 1：按本板实际映射改代码——CH0 对应 bit0，不要用 sigrok 文档的 CH1=bit7。
  - 原因 2：检查接线，把信号接到 CH0 或确认示波器/信号源输出开启；banner 会提示「请检查信号线是否接在 CH0」。
  - 原因 3：电平整段不变时应显示「电平恒定，无跳变」，不要显示一个伪造的「脉宽 1 秒」。

### 1.10 频率 / 周期测量显示 0

- **现象**：「频率测出来是 0」「测量面板空白」。
- **可能原因**：
  1. 通道映射反了（见 1.9），测的是恒定通道，没有边沿。
  2. 没接信号 / 信号频率超出当前采样率能分辨的范围。
  3. **脉宽显示 `1000000.000000 s`**：样本数被当成秒传，漏除采样率。
- **验证方法**：先按 1.9 确认波形有跳变；再看测量值数量级——出现 `1000000.000000 s` 这种天值就是原因 3。
- **解决方法**：
  - 原因 1/2：按 1.9 修通道映射或接线。
  - 原因 3：打开测量计算处，把传给显示的脉宽从「样本数」改成 `样本数 / rate_hz`（秒）。

### 1.11 波形画在错误的通道上

- **现象**：「接 CH0 的波形显示在 CH1」「通道标签和实际对不上」。
- **可能原因**：
  1. 通道映射搞反（本板 CH0=bit0，sigrok 文档 CH1=bit7 不适用）。
  2. 解码时选错了通道（I2C 的 SCL/SDA 选成同一个会报「SCL 与 SDA 不能相同」）。
- **验证方法**：接一个信号到 CH0 单独采集，看它出现在哪个通道标签下。
- **解决方法**：打开通道位映射代码，改成 `通道 i ↔ bit i`（CH0=bit0、CH1=bit1 …），不要用 sigrok 的 bit7 起始约定。

### 1.12 光标落点不对

- **现象**：「点波形上某点，光标落在别处」「Δt 偏了 70 毫秒」。
- **可能原因**：`xToSample` 缺 `LABEL_W` 偏移，与 `sampleToX` 不互逆 —— 实测偏差 70,664 样本（1MHz 下 70ms）。
- **验证方法**：在波形上放光标，用鼠标悬停读样本号，和实际跳变样本号对比；看是否恒定偏一个固定值。
- **解决方法**：打开 `13_web/static/app.js` 第 265 行，确认 `xToSample` 是 `this.start + (x - LABEL_W) * this.span / Math.max(1, this.W - LABEL_W)` —— 必须先减 `LABEL_W`（=66，左侧标签区宽度），与 `sampleToX` 互逆。

### 1.13 时间轴不显示 / 标签重复 / 不切换单位 / 放大不到边沿

- **现象**：「时间轴一个标签都没有」「标签全是 `185.70µs` 同一个值」「`Δt=10 ns` 却放大不到单边沿」。
- **可能原因**（按概率）：
  1. **标签重复**：`185.70µs` 和 `185.71µs` 按固定 1 位小数都格式化成 `185.7 µs` —— 小数位没有随步长变化。
  2. **一个标签都不画**：相对时间模式下 `kFirst` 还按绝对时间算（5e7），第一轮就超过 `tLimit` 直接 break。
  3. **放大不到单边沿**：`MIN_SPAN=10` 太大，2 个样本才能画出一次跳变。
  4. 极小 span 时轴标签全挤在一起（路线图 R7 提到的设计没覆盖的边界）。
- **验证方法**：F12 看 Console 有无报错；拖动缩放到最小，看最小 span 值；对比相邻标签文本。
- **解决方法**：
  - 原因 1：把标签格式化改成「按步长定小数位」，步长越小小数位越多，不要固定 1 位。
  - 原因 2：打开 `13_web/static/app.js` 第 89 行，确认 `var kFirst = useRelative ? 0 : Math.ceil((t0 - 1e-12) / stepSec);` —— 相对模式必须从 0 起。
  - 原因 3：打开 `13_web/static/app.js` 第 9 行，把 `var MIN_SPAN = 10;` 改成 `var MIN_SPAN = 2;`。

### 1.14 解码解出大量帧错误

- **现象**：「UART 解出来全是乱码 / 一堆 frame error」「I2C 解不出 ACK」。
- **可能原因**（按概率）：
  1. 波特率 / 协议参数设置不对（后端报「波特率必须为正整数」「不支持的协议，可选 uart/i2c/spi/can」）。
  2. 接错通道（I2C 的 SCL/SDA 接反或选成同一个，前端会 toast `I2C 的 SCL 与 SDA 不能相同，请重新选择`）。
  3. 采样数据本身有问题（见 1.7、1.8），波形失真导致解码错。
- **验证方法**：先看波形是否干净（1.9），再核对前端选的协议和参数；F12 → Network 看 `/api/decode` 返回的 `error` 字段。
- **解决方法**：
  - 原因 1：在解码面板把波特率改成信号实际波特率（如 115200），协议选 `uart`/`i2c`/`spi`/`can` 之一。
  - 原因 2：重新选 SCL/SDA 为不同通道，按实际接线选（本板通道 i=bit i）。
  - 原因 3：先按 1.7/1.8 修好采集，再解码。

### 1.15 解码结果内容是乱码 JSON

- **现象**：「解码事件里显示 `{"channel":0,"baud":115200}` 这种原始 JSON，不是人话」。
- **可能原因**：该事件 `kind` 没做格式化，落到了兜底分支，直接把原始对象字符串化显示。
- **验证方法**：F12 → Console；看解码事件列表，确认是某类 kind 统一显示成 `{"...":...}`。
- **解决方法**：打开前端事件格式化函数，为这个 `kind` 补一个格式化分支（如 UART 显示 `CH0 0x55 'U'`），不要让它落到兜底的 `JSON.stringify`。

### 1.16 exe 启动很慢 / 打包失败

- **现象**：「双击 exe 转十几秒才出来」「重新打包报 `PermissionError: [WinError 5]`」。
- **可能原因**（按概率）：
  1. 打包时旧 exe 进程还在跑，文件被锁 → `PermissionError: [WinError 5]`。
  2. 杀毒软件首次扫描 exe 拖慢启动（见 1.17）。
  3. exe 内含 14MB 段 + 依赖，冷启动加载慢。
- **验证方法**：打包报错时看是不是 `[WinError 5]`；启动时观察是不是第一次慢、后面快。
- **解决方法**：
  - 原因 1：打包前先 `taskkill /F /IM LogicWeb.exe`（或对应 exe 名），确认任务管理器里没有残留进程，再跑 `python -I make_app_exe.py`。
  - 原因 2/3：加白名单后首次扫描只发生一次；若持续慢，检查是否被反复扫描。

### 1.17 杀毒软件报警

- **现象**：「打包出来的 exe 被报病毒」「frida/抓包工具被隔离」。
- **可能原因**：
  1. PyInstaller 打包的自解压 exe 行为特征被误报。
  2. 逆向/抓包类工具（如 frida 注入）本身会被安全软件标记。
  3. exe 内包含反汇编/驱动访问代码，静态特征触发启发式检测。
- **验证方法**：看杀软报的具体病毒名和路径，确认是不是自己刚生成的 `13_web/dist_app/LogicWeb.exe` 或 `11_pack/dist/LogicScope.exe`。
- **解决方法**：
  - 在杀毒软件里把 `项目根目录` 整个目录加入白名单/信任区；Windows Defender：设置 → 隐私和安全性 → Windows 安全中心 → 病毒和威胁防护 → 排除项 → 添加文件夹。
  - 不要为了「过杀软」去改打包脚本的签名逻辑；这是误报，加白名单即可。若必须用 frida 抓包，临时退出实时防护，用完恢复。

## 2. 按错误码速查

| 错误码 | 名称 | 含义 | 最常见原因 | 解决 |
|---|---|---|---|---|
| 87 | `ERROR_INVALID_PARAMETER` | 参数错误，所有 pipe 操作失败 | alt setting 0 没有端点，必须切到有端点的 alt 1 | 切 alt 1（`winusb.py::_select_endpoint_alt_setting`）。**不要拔插设备** |
| 121 | `ERROR_SEM_TIMEOUT` | 读/写超时，设备不吐数据 | ① 设备未初始化（缺 `0x82`）；② 明文命令写入后设备不响应 | ① 先跑一次 Logic.exe 再关；② 命令改加密 `d5 8e` |
| 5 | `ERROR_ACCESS_DENIED` | 权限不足/设备被占用 | `LogiScope.exe` / `Logic.exe` 还开着；或没装 WinUSB 驱动 | 关掉占用程序后刷新；确认驱动已装。**不用拔插** |
| **31** | `ERROR_GEN_FAILURE` | 设备已断开 | 固件挂起，`Get-PnpDevice` 看着在但端点全不响应 | **物理拔插**：拔 USB 线等 5 秒再插，然后跑一次 Logic.exe |
| 32 | `ERROR_SHARING_VIOLATION` | 设备正被另一进程占用 | 另一个采集进程攥着句柄 | 关掉占用进程（`taskkill`），不用拔插 |
| 1167 | `ERROR_DEVICE_NOT_CONNECTED` | 设备不存在 | 线松了 / 设备真断开 | 检查 USB 线，必要时拔插 |

> 数字核对：`ERROR_GEN_FAILURE` 的 Windows 实际值是 **31**（`winusb.py` 第 140 行也是这样映射的，已用 `Win32Exception(31)` 复核）。早期草稿误记成 59，59 实际是「意外的网络错误」，与本项目无关。**遇到 31 按 5.1 拔插处理。**

## 3. 诊断命令集（从浅到深）

按顺序跑，每条带预期输出和「说明什么」。前面的过了再跑后面的。

### 3.1 设备在不在
```bash
powershell -NoProfile -Command "Get-PnpDevice -PresentOnly | Where-Object {$_.InstanceId -match '0925'} | Format-Table Status,FriendlyName"
```
- **预期**：`Status=OK`，FriendlyName 含 Saleae/Logic 字样。
- **说明什么**：空列表 = 没插好/驱动没装/已断开；有但后面操作全失败 = 固件挂起（见 5.1）。

### 3.2 端点表对不对
```bash
cd 03_host
python -I winusb.py
```
- **预期**：打印枚举结果，列出 `0x01`(OUT 命令)、`0x81`(IN 应答)、数据 IN 端点等。
- **说明什么**：`枚举结果：[]` = 设备没找到；**实测结论（2026-11-25 复核）**：**未初始化**状态为 `alt=1`、6 端点表（`0x01 0x81 0x02 0x04 0x86 0x88`），此时无 `0x82`、采不到数据；经原厂软件初始化后为 `alt=0`、4 端点表（`0x01 0x81 0x82 0x06`），数据端点即 `0x82`。 alt 0 下看不到端点要先切 alt 1。

### 3.3 能不能打开设备
```bash
cd 13_web
python -I launcher.py --self-check
```
- **预期**：打印 `自检完成：端口=xxxx 设备={...}`，`device` 里 `occupied=false`、`initialized=true`。
- **说明什么**：报「设备打开失败：可能被其它程序占用」→ 5.2；报「未检测到设备」→ 3.1；报「缺少 0x82 端点」→ 1.4 原因 2。

### 3.4 能不能写命令
```bash
cd 08_fx2
python -I capture_fx2.py --rate 1000000 --seconds 3 --out probe.bin
```
- **预期**：正常应该开始采集并写出文件；若报 `写管道 0x01 失败：参数错误(87)` → alt setting 错。
- **说明什么**：写入成功但随后 0 字节 → 命令没加密（明文 `01 2f` 无效，改 `d5 8e`）。

### 3.5 能不能读到数据
```bash
python -I capture_fx2.py --rate 1000000 --seconds 3 --probe
```
- **预期**：逐个端点打印试读结果，指出哪个端点读到大量数据。
- **说明什么**：`0x81` 只回 1 字节 ack 是正常的；**实测结论（2026-11-25 复核）**：**未初始化**状态为 `alt=1`、6 端点表（`0x01 0x81 0x02 0x04 0x86 0x88`），此时无 `0x82`、采不到数据；经原厂软件初始化后为 `alt=0`、4 端点表（`0x01 0x81 0x82 0x06`），数据端点即 `0x82`。 哪个端点吐 1.5MB 就用哪个，以实测为准。

### 3.6 服务起没起
```bash
curl -s http://127.0.0.1:8421/api/status
```
- **预期**：`{"ok":true, "device":{...}, "rates":[...], "version":...}`。
- **说明什么**：连不上 = 服务没启动或端口不是 8421（看黑框「实际端口」）；`ok:false` 且带 `error` = 后端自检没过，看 3.3。

### 3.7 静态资源有没有
```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8421/static/style.css
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8421/static/app.js
```
- **预期**：两行都是 `200`。
- **说明什么**：`404` = HTML 里路径写错（应为 `/static/style.css`，见 1.3）；`403` = 后端判定路径越界或文件类型不支持。

### 3.8 前后端能不能通
```bash
curl -s -X POST http://127.0.0.1:8421/api/capture -H "Content-Type: application/json" -d "{\"rate_hz\":1000000,\"seconds\":1}"
```
- **预期**：返回 `{"ok":true, "id":...}` 或明确的 `{"ok":false,"error":"..."}`。
- **说明什么**：HTTP `400` = 参数错（采样率/时长/通道不在范围）；`409` = 设备占用/采集中/未就绪（看 `error` 文案）；`403` = 禁止访问；`404` = 路由或采集编号不存在。前端 toast 显示的就是这里的 `error` 字段。

## 5. 什么时候该拔插，什么时候不该

见表 5.1 与 5.2。**先判断再动手**，拔插是最贵的操作，别一上来就拔。

### 5.1 必须物理拔插

| 情况 | 判据 | 做法 |
|---|---|---|
| 设备固件挂起 | `ERROR_GEN_FAILURE`（码 31）；`Get-PnpDevice` 显示 OK 但所有端点操作失败 | 拔 USB 线 → 等 5 秒 → 插回 → 确认 `Status=OK` → 跑一次 Logic.exe 再关 → 重测 |
| 设备真的断开了 | `ERROR_DEVICE_NOT_CONNECTED(1167)`；枚举结果 `[]` 且线确认插着 | 检查 USB 线/接口，必要时换线或换口，然后按上面流程 |

### 5.2 不用拔插（拔了也白拔，浪费时间）

| 情况 | 判据 | 正确做法 |
|---|---|---|
| alt setting 错 | `ERROR_INVALID_PARAMETER(87)`，所有 pipe 操作失败 | 切到 alt 1（有端点的那档），**不拔插** |
| 设备未初始化 | `ERROR_SEM_TIMEOUT(121)`，提示缺 `0x82`/请先启动 Logic.exe | 跑一次 Logic.exe 再关，点 banner 刷新，**不拔插** |
| 命令没加密 | 写入成功但读回 0 字节 | 命令从明文 `01 2f` 改成加密 `d5 8e`，**不拔插** |
| 设备被占用 | `ERROR_ACCESS_DENIED(5)` / 徽章「设备被占用」 | 关掉 `LogicScope.exe`/`Logic.exe`，**不拔插** |
| 数据量少 / 达成率低 | 采集成功但文件大小远小于预期、达成率 84.8% | 加并发读线程、修达成率分母，**不拔插** |
| 服务端口占用 | 启动报端口被占 / 8421 连不上 | 换端口或杀进程（见 5.3），跟设备无关 |

### 5.3 服务端口占用怎么处理（和设备拔插无关）
```bash
netstat -ano | findstr :8421
taskkill /F /PID <上面查到的PID>
```
或者启动器本来就会从 8421 自动找到第一个空闲端口（8421~8430），直接看黑框「实际端口：xxxx」，用新端口访问即可，不必杀进程。

## 7. 已知无法修复的问题

以下是**硬件/设计层面**的限制，按上面步骤折腾也不会变好，**别浪费时间**。

1. **硬件触发彻底没戏**：逻辑分析仪的触发是**软件触发**（libsigrok 源码已确认）。除非逆向出 FX2 固件的触发寄存器并自己实现，否则没有真正硬件触发。路线图 R6 明确写了这条。不要因为「触发不灵敏」反复拔插或重装。
2. **克隆板端点布局与原厂文档描述不同**：开源文档与早期分析对端点位置有不同说法。**实测结论（2026-11-25 复核）**：**未初始化**状态为 `alt=1`、6 端点表（`0x01 0x81 0x02 0x04 0x86 0x88`），此时无 `0x82`、采不到数据；经原厂软件初始化后为 `alt=0`、4 端点表（`0x01 0x81 0x82 0x06`），数据端点即 `0x82`。 早期文档曾把「未初始化状态」误记为「硬件差异」，已更正。若你的板子实测与此不符，以你自己 `list_pipes()` 的输出为准。
3. **固件挂起后主机侧无法复位**：FX2 在错误状态下运行时，主机侧无法用软件复位，只能断电重连。这是芯片特性，不是驱动 bug。遇到 `ERROR_GEN_FAILURE` 老老实实拔插。
4. **官方初始化参数包尚未实现**（当前版本限制，非硬件）：`Logic.exe` 的 `Logic2FpgaDevice::SetCaptureParameters` 要下发 10 个采集参数到 FPGA，我们的代码目前只做了 alt setting 切换和下发启动命令，缺这一步，所以冷启动必须先跑一次 Logic.exe。详见 `08_fx2/设备状态与恢复.md`。
5. **极小 span 下轴标签会挤在一起**：路线图 R7 提到「566 行设计文档落地时会有没覆盖的边界，如极小 span 时轴标签全挤在一起」。这是设计边界，遇到时手动缩放规避，不必当故障排查。
