## 0. 一句话总览

这是一台某宝克隆版 Saleae Logic 逻辑分析仪：USB VID `0x0925` / PID `0x3881`，Cypress FX2（CY7C68013）桥接 8 路纯数字通道，USB High Speed。主机侧用 WinUSB 免驱通信，数据从端点 `0x82` 批量 IN 流出，命令从 `0x01` 批量 OUT 写入，**命令字节必须经过一套有状态混淆算法加密，否则设备不吐数据**。采集前必须先跑一次官方 Logic.exe 做初始化，否则端点表不对、数据端点 `0x82` 根本不存在。采样率 10 档，从 200 kHz 到 24 MHz；达到满速的必要条件是**至少 3 个并发读线程 + 64 KB 缓冲**。

一句话记住三个坑：**先跑 Logic.exe、命令加密、多线程读**。踩中任意一个的反面都会得到"设备看起来正常但采不到数据"的同一症状。

### 1.3 为什么显示 Lakeview Research

INF 的 `[Strings]` 节里，产品描述字符串把 `0925:3881` 命名为 "Logic"，厂商字段沿用了原厂的历史名称 **Lakeview Research**（Saleae 早期公司名）。克隆板直接照抄了这个 VID/PID，于是 Windows 依据 INF 把它识别成 "Lakeview Research / Saleae Logic"。

## 2. 端点与初始化状态

### 2.1 两种状态的端点表（含 alt setting）

设备插上后**必须先启动一次 Logic.exe、等它识别到设备、再关掉**，之后我们自己的代码才能正常采集。这一步会改变设备的端点布局，实测对比如下（来源：真机验证结果.md、`capture_verified.py` 头部注释）：

| 状态 | alt setting | 端点表（`list_pipes()` 顺序） | 数据端点 0x82 |
|---|---|---|---|
| 未初始化（冷插上、没跑 Logic.exe） | 1 | `0x01 0x81 0x02 0x04 0x86 0x88`（6 个） | **不存在** |
| 已初始化（跑过 Logic.exe 并关闭） | 0 | `0x01 0x81 0x82 0x06`（4 个） | 存在 |

各端点用途（已初始化状态）：

| 端点 | 方向 | 用途 |
|---|---|---|
| `0x01` | OUT | 命令端点（EP1 OUT），写加密后的启动命令 |
| `0x81` | IN | 命令应答端点（EP1 IN），只回 1 字节 |
| `0x82` | IN | **数据端点（EP2 IN）**，采样流从这里持续吐出 |
| `0x06` | IN | 出现在表中，本项目未使用 |

**关于 alt setting 的反转，必须如实交代：** 常规预期是"初始化后用 alt 1"，`winusb.py` 的注释与旧文档甚至还写着"Saleae 把端点都放在 alt 1 上、alt 0 是 0 个端点"，但实际实测恰好相反——未初始化时是 alt 1 有 6 个端点，初始化后变成 alt 0 有 4 个端点，数据端点也从 `0x88`（旧推测）变成了 `0x82`。**这个反转是实测现象，原因未查明**（推测与克隆板 FPGA 配置或 FX2 固件重枚举有关，但没有任何实验证实，不要当成结论引用）。工程上的处理办法不依赖原因：`winusb.py::_select_endpoint_alt_setting()` 会在 open 时探测并切换到"第一个有端点的 alt setting"，`capture_verified.py` 则直接检查 `0x82` 是否存在来判断设备是否就绪。

### 2.2 诊断命令

在设备已插好、且已跑过一次 Logic.exe 的前提下，打印当前端点表（一行命令，跑完即关，不会驻留占用设备）：

```
cd 03_host
python -I -c "import sys;sys.path.insert(0,'.');import winusb;d=winusb.SaleaeDevice(winusb.enumerate_devices()[0]['path']);d.open();print('alt=',d.alt_setting);print([(hex(p),t,m) for p,t,m,i in d.list_pipes()]);d.close()"
```

预期输出（本机 2026-11-25 实跑，已初始化状态）：

```
alt= 0
[('0x1', 'Bulk', 512), ('0x81', 'Bulk', 512), ('0x82', 'Bulk', 512), ('0x6', 'Bulk', 512)]
```

输出里三个数字依次是：端点地址、类型（全是 Bulk）、最大包长（512 字节，High Speed 批量端点上限）。`-I` 隔离模式是必需的：它会跳过当前目录的 `sitecustomize.py` 之类的注入，避免误加载不可信模块；`sys.path.insert(0,'.')` 再把 `winusb.py` 所在目录显式加回来。

异常输出与含义：

- `IndexError: list index out of range` —— `enumerate_devices()` 返回空，设备没插好或驱动没装。回到 1.2 确认 `Status=OK`。
- `alt= 1` 且列表里有 `0x88`、没有 `0x82` —— 设备未初始化，跑一次 Logic.exe 再关。
- `读管道 ... 121` 或控制传输 121 超时 —— 设备固件挂起，只能物理拔插（见 `设备状态与恢复.md`）。

### 2.3 状态判断表

| 看到的端点表 | 当前状态 | 该怎么办 |
|---|---|---|
| `0x01 0x81 0x82 0x06`，alt=0 | 已初始化，可采集 | 直接进入第 3 节，跑采集 |
| `0x01 0x81 0x02 0x04 0x86 0x88`，alt=1（无 `0x82`） | 未初始化 | 启动 Logic.exe，等识别到设备后关闭，再跑诊断命令复查 |
| 枚举不到设备 / `Status≠OK` | 未连接或驱动异常 | 检查 USB 线、换口；确认 INF 的 WinUSB 驱动已装 |
| 枚举正常但所有端点读写报 121 超时 | 固件挂起 | 物理拔掉 USB 线、等 5 秒、插回，再跑 Logic.exe；主机侧无法复位 |

## 3. USB 命令协议（本篇核心）

### 3.1 完整时序

下面 6 步是 `capture_verified.py::capture()` / `capture_mt()` 的实现顺序，**按时间顺序，不可调换**：

```
1. open_dev()            打开设备、设管道策略（超时/RAW_IO/忽略短包）
2. drain                 读空 EP 0x82 残留（8 次 100ms 超时读，丢掉上次采集的尾巴）
3. 启动 3 个读线程        在 0x82 上阻塞等数据（先就位，还没发命令）
4. 发命令                 写 EP 0x01，内容是加密后的 {0x01, delay}
5. 设备开始吐数据         0x82 持续有数据，读线程循环 64KB 块收进 chunks
6. 到时停止               置 stop 标志、join 线程、拼接 chunks
```

对应代码位置：`open_dev()` 在 `capture_verified.py:88-102`，drain 在第 172-176 行（多线程版），线程创建与命令发送在第 178-183 行，停止在第 185-190 行。`delay` 与采样率的换算见 4.1。

### 3.2 为什么顺序不能反

**为什么必须先起读线程、再发命令？** 设备收到启动命令后会立刻开始往 FX2 的 FIFO 里填采样数据，FIFO 容量有限；如果这时主机端还没有线程在 `0x82` 上阻塞读取，填入的数据会一直堆积，FIFO 满后被**新数据覆盖**。实测现象是：先发命令再起线程，开头几百毫秒的数据会丢失——这段时间足够让 FIFO 溢出好几次。所以对读线程还额外 `sleep(0.2)` 确保它们已经进入阻塞读状态，然后才写命令。

**为什么发命令前要 drain？** 上一次采集可能留下未读干净的数据残留在 `0x82`；不排空的话这些旧字节会混进本次结果开头，造成"前几个样本对不上信号"的假象。drain 用 100ms 短超时读 8 次，读不到就放弃，不阻塞流程。

### 3.3 混淆算法实现

完整实现（可直接复制到 Python 3 运行；这段代码与 `capture_verified.py::obfuscate()` 完全一致）：

```python
def obfuscate(plain):
    out, A, B = [], 0x54, 0x9B
    for p in plain:
        t = A ^ p
        t ^= 0x2B
        t = (t - 5) & 0xFF
        t ^= 0x35
        t = (t - 0x39) & 0xFF
        t ^= B
        t ^= 0x5A
        t = (t + 0x50) & 0xFF
        t ^= 0x38
        t = (t - 0x45) & 0xFF
        out.append(t)
        B, A = p, t
    return bytes(out)
```

算法要点：初值 `A=0x54`（上一个密文字节）、`B=0x9B`（上一个明文字节）。每处理一个明文字节都更新状态 `B, A = p, t`，所以它是**有状态**的——不能用无状态的逐字节替换表代替，同一明文在不同位置会加密成不同密文。全部运算在 8 位内进行（每步 `& 0xFF`），对应原厂程序某函数的反汇编结果。

### 3.5 为什么必须加密

这是本项目踩过的最大的坑，如实记录实测对比（来源：真机验证结果.md）：

| 发送内容 | 写入结果 | 设备行为 |
|---|---|---|
| 明文 `01 2f` | `write_pipe` 成功，返回 2 字节 | **完全不吐数据** |
| 密文 `d5 8e` | `write_pipe` 成功，返回 2 字节 | **立刻吐出约 1.5 MB 数据** |

关键结论：

- 明文**写入成功但设备沉默**。也就是说不能靠写操作的返回值判断协议是否正确——返回值只说明"数据交给 USB 了"，不代表固件接受。
- 曾假设"明文也能用、混淆是上位机多此一举"，实测**排除了这个假设**：同一套代码、同一台设备，只改命令内容就能从"零数据"变成"满速数据"。
- 混淆层确实是 Saleae 上位机自己加的（从 Logic.exe 反汇编出来），但**固件端确实在校验**——否则明文也该出数据。

因此排查"不出数据"问题时，命令加密是优先级最高的检查项之一：用 3.4 的向量表先确认算法，再看 2.3 的端点状态。

## 4. 采样率与数据格式

### 4.1 采样率表

`delay` 与采样率的关系是 `delay = 48000000 / rate - 1`（FX2 的 48 MHz 时钟分频），10 档全部固化在 `capture_verified.py::RATES` 中。可用 `python -I capture_verified.py --list` 列出。

| 采样率 | delay（十进制） | delay（hex） | 理论带宽（8 通道 × 采样率） | 实测达成率（3 线程 / 64KB） |
|---|---|---|---|---|
| 24 MHz | 1 | 0x01 | 24 MB/s | 100% |
| 16 MHz | 2 | 0x02 | 16 MB/s | 100% |
| 12 MHz | 3 | 0x03 | 12 MB/s | 100%（wall-clock 量法曾误报 58%~68%，见下注） |
| 8 MHz | 5 | 0x05 | 8 MB/s | 100% |
| 4 MHz | 11 | 0x0b | 4 MB/s | 100% |
| 2 MHz | 24 | 0x18 | 2 MB/s | 未单独实测 |
| 1 MHz | 47 | 0x2f | 1 MB/s | 未单独实测 |
| 500 kHz | 95 | 0x5f | 0.5 MB/s | 未单独实测 |
| 250 kHz | 191 | 0xbf | 0.25 MB/s | 未单独实测 |
| 200 kHz | 239 | 0xef | 0.2 MB/s | 未单独实测 |

注：`capture_verified.py::capture_timed()` 单独测量"数据实际流动时间窗"后，4 MHz 为 101%、8 MHz 为 100.5%；12 MHz 用包含线程启动的墙钟时间量曾得 68%，但用数据窗量法与同步读法复测可满载，**以 100% 为准**。标注"未单独实测"的档位代表本手册不对其性能作承诺，但 delay 值来自已验证的分频公式。

交叉验证分频公式的实测证据（8 kHz 方波，来源：真机验证结果.md）：四档采样率下主 run 长度分别为 750 / 500 / 250 / 63 样本（12/8/4/1 MHz），比例 750:500:250 严格等于 12:8:4，说明 `48MHz/rate-1` 的分频算法正确。

### 4.2 数据格式

每次读 `0x82` 得到的是裸字节流，**每个字节代表一个采样时刻的 8 个通道电平**：

```
bit7  bit6  bit5  bit4  bit3  bit2  bit1  bit0
 CH7   CH6   CH5   CH4   CH3   CH2   CH1   CH0
```

- `bit=1` 表示该通道此刻为高，`bit=0` 为低。
- 未接线的通道读作高（内部上拉），因此空闲时字节常是 `0xFF`。
- 通道映射 **CHn → bitn（CH0=bit0 … CH7=bit7）**。这与 sigrok 文档记载的"Probe 1 在 MSB、Probe 8 在 LSB"**完全相反**，是本机克隆板实测结果，不要照搬 sigrok 的说法。

解析示例：假设采到一段字节 `FF FE FF FE FF FF`，按 bit0 解码：

```
样本:   FF      FE      FF      FE      FF      FF
bit0:    1       0       1       0       1       1
```

bit0 在 1/0 间交替，说明 CH0 上有一个方波。从 Python 里取单通道序列的写法：

```python
import numpy as np
data = np.frombuffer(blob, dtype=np.uint8)   # blob 是采集得到的原始 bytes
ch0 = (data >> 0) & 1
ch7 = (data >> 7) & 1
```

### 4.3 通道映射验证方法

这是最容易搞错、后果最严重的地方（映射错会让所有解码结果整体翻转）。**实测验证法**：把一个已知频率的方波（例如示波器输出 50 kHz）接到 CH0，采一小段，然后检查数据集：

- 如果 `set(data)` 是 `{0xFE, 0xFF}`，说明只有 bit0 在变 → CH0 = bit0。
- 如果看到的是 `{0x7F, 0xFF}`，说明只有 bit7 在变 → CH0 = bit7（即 sigrok 的映射），那这台设备的映射与本项目不同，需要按实测结果改代码。

完整验证脚本（假设方波已接 CH0，设备已初始化；保存为任意临时 `.py` 后用 `python -I` 运行，或用 `python -I - <<'EOF'` 喂入）：

```python
import sys
sys.path.insert(0, r'03_host')
sys.path.insert(0, r'08_fx2')
import winusb, capture_verified as cv

d = winusb.SaleaeDevice(winusb.enumerate_devices()[0]['path'])
d.open()
assert '0x82' in [hex(p) for p, _, _, _ in d.list_pipes()], '设备未初始化，先跑 Logic.exe'
blob = cv.capture_mt(d, delay=47, seconds=0.5, n_readers=3)  # 1MHz
d.close()
vals = set(blob)
print('distinct values:', sorted(vals)[:12])
print('CH0=bit0 ?', vals == {0xFE, 0xFF})
```

## 5. 性能与限制

### 5.1 实测性能

本机（Windows 10 x64）实测，目标时长 2 秒，缓冲 64 KB（来源：`capture_verified.py` 注释、真机验证结果.md）：

| 采样率 | 单读线程成功率 | 3 读线程成功率 | 备注 |
|---|---|---|---|
| 4 MHz | 25%~100%（波动） | 100% | 单线程偶尔能过，不可靠 |
| 8 MHz | 0.5% | 100% | 单线程基本不可用 |
| 12 MHz | 0.4% | 100% | 单线程几乎必然丢数 |
| 24 MHz | 未实测单线程 | 100%（24 MB/s 满速） | 3 线程 + 64KB 缓冲 |

信号质量实测（50 kHz 方波 @ 24 MHz 采样）：频率 49,994.5 Hz（相对 50 kHz 误差 0.01%）、占空比 49.79%、边沿抖动 P1~P99 为 1 个样本。说明在多线程满速采集下，数据不仅"数量对"，"时间精度"也可靠。

### 5.2 为什么必须多线程

**为什么同步 `read_pipe` 单线程在 8 MHz 以上几乎必然丢数？** 因为 WinUSB 的 `read_pipe` 是同步调用：一次调用返回后，CPU 要先把这批数据 append 进列表，再发起下一次调用；这两次调用之间存在一个**用户态间隙**。FX2 的 FIFO 在这段间隙里仍在被硬件持续填充，间隙长度只要足够让 FIFO 写满，后续采样就会**覆盖尚未被读走的数据**。8 MHz × 1 字节 = 8 MB/s，间隙哪怕只有几十微秒也足以溢出。实测单线程在 8 MHz 只有 0.5% 成功率，正是这个原因。

**为什么 3 个线程 + 64 KB 就能解决？** 多个线程轮流在 `0x82` 上阻塞读，一个线程在数据拷贝时另一个已经挂在读调用上，间隙被互相填补，FIFO 始终有人排空。64 KB 缓冲则让单次系统调用搬走足够多的数据，摊薄调用开销。这是实测结论，不是推测：3 线程在 4/8/12/24 MHz 四档全部 100% 满速。注意线程数不是越多越好，3 个是实测够用的配置。

### 5.3 硬件上限

24 MHz × 8 通道 × 1 字节/通道 = **24 MB/s**，这是 FX2 芯片在 USB High Speed 下的实际吞吐天花板。再提高采样率，USB 带宽和 FIFO 都会成为瓶颈——这不是靠优化主机代码能突破的。`capture_verified.py` 的注释也记录了一个细节：多线程路径在约 12 MB/s 以上会出现平台期（取决于机器），但最终 24 MHz 满速实测可达 24 MB/s。

### 5.4 做不到的事

以下能力**本机设备与现有代码均不具备**，不要在设计时假设它们存在：

- **硬件触发**：没有发现任何触发寄存器协议，现有实现只做持续流式采集，无法"等某个通道出现边沿再开始存"。软件上后处理可以筛选，但那不叫硬件触发。
- **模拟通道**：这是纯数字 8 通道设备，没有 ADC。Logic.exe 里有 `InitAdc` 之类的字符串不能当作本机有模拟输入的证据——本机实测只有数字通道。
- **超过 8 通道**：硬件只有 8 路数字输入，CH0~CH7，无法扩展。
- **`.logicdata` 原生格式导出**：尚未逆向该格式，目前只能导出 CSV / VCD（证据：真机验证结果.md「还没做的」）。

> 说明：旧文档曾推测"24 MHz 可能丢包"，但后续实测已推翻——24 MHz 在 3 线程下 100% 满速。此处以最新实测为准。
