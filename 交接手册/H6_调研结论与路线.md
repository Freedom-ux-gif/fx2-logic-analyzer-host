# H6 调研结论与路线

> 本篇不是调研摘要，是**决策文档**。目标是让读者不读完 2902 行原始调研，就能判断「下一步做什么、不做什么、为什么是这个顺序」。
> 输入：R1–R10 共 2902 行原始调研 + 大脑实测现状。基准现状：采集 24MHz 满速、8 通道波形、缩放平移光标、时间轴（ns/µs/ms/s 自动切换）、UART/I2C/SPI/CAN 解码、测量侧栏、CSV/VCD/二进制导出、网页版 exe；已修 `xToSample` 偏移 / 采样率下拉被冲 / 渲染性能 44.9ms→6.2ms。

## 0. 一句话结论

**该做的只有一件事：把「AB 区间标记 + 区间统计」落地（R7 已给到可照抄的设计，且是用户点名的唯一未完成项）；紧随其后补两个地基——解码器参数自声明 schema、后端区间解码与分页；会话保存留到 P1。不该做的是硬件触发、模拟通道和 R4 列出的 5 类协议——前两者是物理天花板，后者是采样率/被动监听的结构性限制，投入再多软件工作也换不来。**

判断逻辑很简单：**用户点名 > 三家标配缺失 > 能解锁后续 > 成本低**。按这四条排，时间线已经完成、渲染已经优化到位，路线图里原本的三件 P0 只剩两件；而「功能太少」的抱怨主要靠 AB 区间和虚拟通道缓解，不是靠硬堆解码器。

## 2. 优先级排序（本篇核心）

### 2.1 排序依据（明确权重）

不用「用户抱怨 > 业界标配」这种无法计算的模糊排序。定义可复算的粗分：

**优先级分 = 5×用户明确点名 + 3×三家标配缺失 + 3×地基性（解锁后续功能）+ 2×实现成本低 + 1×单家特色**

权重解释：

- **用户明确点名 = 5（最高）**：R7 §0.1 记录了三句原话——「不知道时间概念」「标定 AB 之间脉冲数、AB 之间的时间」「占空比啥的数据」。其中时间线**已经做完**，剩下两句全部落在 AB 区间与区间统计上。
- **三家标配缺失 = 3**：来自第 1 节覆盖度标签。三家都有说明这是用户心智里的「本来就该有」，缺了是硬伤。
- **地基性 = 3**：解码参数 schema、Region 统一结构、后端 window 这类功能本身不可见，但不做它们，后面每一项都要返工。
- **实现成本低 = 2**：R7 给了 5 小时完整设计、R10 给了 20~25 行的 API 改造、R8 已把渲染降到 6.2ms——这些都是「今天就能交付」的信号。
- **单家特色 = 1**：只有一家有，说明可能是差异化优势，也可能是伪需求，权重最低。

**平局裁决顺序**：用户点名 > 地基性 > 成本 > 依赖少。

## 3. 三个「不做」的决策

每条按「谁想做 → 为什么不该做（具体到源）→ 非要做需要什么」写。

### 3.1 硬件触发

- **谁想做**：看到 DSView 有 16 级 Stage + Serial 触发、Logic 2 有 Trigger View 的人，会自然问「我们为什么不能硬件触发」。
- **为什么不该做（依据）**：
  1. **协议层**：大脑实测（R6 S9）只逆出「设采样率 + 启动采集」一条命令，**触发寄存器协议完全未逆出**，已知命令还需混淆，没有任何下发触发条件的通道。
  2. **固件/软件栈层**：sigrok wiki `Saleae_Logic` 页（R6 S2）把原版 8 通道 Logic 标为 `none (SW-only)`；`Fx2lafw` 页（R6 S1）设备表**没有任何触发能力字段**，8/16 探针全部 24MHz 晶振。
  3. **机制层**：sigrok 触发分两层——硬件触发在驱动层，软件触发在主机侧 `soft-trigger.c`（R6 S5），其 `pre_trigger_buffer` 是主机环形缓冲、深度由内存决定；FX2 内部 FIFO 仅 4×512 字节量级，克隆板 Buffer/ESD 是 74HC 系列而非 RAM（R6 §5 #5），即使固件触发也只有极浅预触发。
  4. **硬件层**：Cypress FX2（CY7C68013A）**没有专用逻辑触发外设**，触发只能在固件循环里比较（占 8051 周期）或主机全量匹配两条路径实现（R6 §1.2）。
  5. 结论：当前「先采全量到内存、离线找触发点、保留预触发」是**唯一可行路径**，与 sigrok 软件触发同构。
- **如果非要做需要什么**：逆出触发配置命令（类型寄存器、通道掩码、边沿/电平条件、预触发深度的字节格式 + 混淆算法）；用 USB 抓包对比「设触发」前后控制传输；施加已知边沿验证 0x82 端点是否只在边沿后返回数据（确认克隆固件是否阉割）。R6 §1.4 明确判定「工作量大、收益不确定，建议不投入」。

### 3.2 模拟通道

- **谁想做**：三家都有模拟同屏，用户看到截图会问「我们能不能也画模拟波形」。
- **为什么不该做（硬件依据）**：
  1. 大脑实测（R6 S9）：设备 0925:3881 是 8 通道**纯数字、无 ADC**，EP 0x82 每字节 8 位对应 8 个数字通道，**没有模拟码流通道**。
  2. `Fx2lafw` wiki 两条脚注（R6 S1）直接命中这块板：「Analog signal support is not yet implemented」以及「即使与 USBee AX-Pro 同 VID/PID，该设备也只有 8 通道、无模拟支持」——**同 VID/PID 不等于有模拟**。
  3. 模拟通道缺一不可的三件套：ADC 芯片 + 模拟前端（保护/增益/抗混叠）+ FX2 额外 PD 口引脚与端点（R6 §2.1 / S1 原文 "For analog support PD0-PD7 (plus additional hardware) is usually used"）。本板 PB0–PB7 已被 8 数字通道占满，无额外硬件。
  4. Logic 2 官方（R3 S19）还明确：**不能从数字数据生成模拟曲线**（"there is no way to generate an analog graph from digital data"）——软件造不出模拟采样。
- **如果非要做需要什么**：**换硬件**（购买带 ADC 的混合信号设备），这是唯一路径，不属于本项目范围。UI 也不应预留空模拟通道入口（R6 §2.3）——那是永远不产生数据的虚假功能。真正能扩展的是数学/虚拟通道（第 2.2 节第 10 项）。

### 3.3 三类不该做的解码器（从 R4 §6 五项中挑依据最硬的三项）

- **① USB Full/High Speed 抓包**（谁想做：看到 R4 清单里有 `usb_packet` 就想要）：
  - 为什么不该做：全速 12Mbps 需 ≥96MS/s 与差分探头，我们只有 24MHz 单端 `channel_bits`；无法捕获 USB 差分 SE0/双单端零状态，NRZI + bit-stuffing 对采样抖动极敏感（R4 §6 #1）。高速 480Mbps 远超能力。
  - 非要做需要：外置高速差分采集硬件 + ≥100MS/s 采样率；低速 1.5Mbps 仅可作远期低优先级。
- **② 需要模拟前端的协议**（`aud` 模拟音频、RF 解调类 `ook_oregon` 原始载波等）：
  - 为什么不该做：逻辑分析仪只采数字电平，无 ADC / 无带通滤波，无法直接解码模拟调制信号（R4 §6 #3），与 3.2 是同一个物理瓶颈。
  - 非要做需要：外部解调器/比较器先把信号转成数字再接入——那是增加硬件，不是加解码器。
- **③ 超高速串行（PCIe / SATA / 1000BASE-T）**：
  - 为什么不该做：采样率要求 GHz 级，且 **sigrok 132 个解码器清单本身就不含这类协议**（R4 §6 #4），纯 numpy 边沿检测无法胜任，需专用协议分析仪。
  - 非要做需要：专用高速串行分析仪硬件，与本项目无关。

> 另外两类（并行总线高位宽/高速、需要主动握手的协议如完整 USB 枚举/JTAG 链自动探测）同样不做：前者缺多通道偏斜校准与双边沿 DQS，后者逻辑分析仪是**被动监听设备**，无法发命令完成枚举协商（R4 §6 #2/#5）。

## 4. 未决的技术选型

四项都需要人拍板，本篇给建议和理由，不假装已定。

### 4.1 会话文件格式：ZIP 还是单文件

- **选项 A**：ZIP 容器（`.lcaps`），内部分 `meta.json` / `waveform.bin` / `decoders.json` / `view.json` / `thumbnail.png` / `notes.md`（R9 §5.1–5.3，24 字段 schema）。
- **选项 B**：单文件裸二进制拼接（自定义分界与偏移表）。
- **建议**：**选 A（ZIP）**。
- **理由**：R9 §5.1 给的四条理由成立——① 自描述+多文件，元数据/波形/视图可独立版本化、按需跳过；② 与 `.sr`/`.sal` 同思路，`unzip -l` 可直接排错；③ 压缩按条目控制，波形默认 store 保证 48MB 加载速度，文本元数据 deflate 收益大；④ ZIP64 远超需求。选项 B 需自定义偏移表、易损坏且不可局部访问；SQLite 引入依赖与分享不便。体积实测估算：store 约 45.9MiB，deflate 约 23MiB，都在可接受范围。

### 4.2 解码器参数：要不要改成「自声明 schema」

- **选项 A**：类级 `OPTIONS` 声明（参考 R4 §4.3 #3、R3 §10 的 `StringSetting/NumberSetting/ChoicesSetting`），前端自动生成表单。
- **选项 B**：维持函数入参 + 手写配置 UI。
- **建议**：**选 A，且它是第 2 位的 P0，必须先于新解码器**。
- **理由**：R4 §4.3 把我们缺的 7 项机制列全了（分层解码、多粒度注解、选项声明、采样率自检、错误事件、二进制/元数据输出、边沿等待），其中选项声明是**地基**——不做它，第 8 项的 5 个解码器每个都要手写一遍配置 UI，且无法像 sigrok-cli 那样用 `uart:baudrate=115200:parity=odd` 文本串复现实验（R5 §1.3 可抄点 #7）。成本 6h，收益是解锁后续所有解码器。

### 4.3 渲染：要不要上 OffscreenCanvas

- **选项 A**：上 OffscreenCanvas + Worker（R8 §2.4，第二阶段）。
- **选项 B**：先不上，维持主线程 + rAF 节流 + 三段策略（R8 §4.1）。
- **建议**：**选 B，暂不上；列为「只有实测仍有 jank 才做」的条件项**。
- **理由**：R8 阶段 1 的 Uint32 批量 min/max 已落地（大脑实测 6.2ms，R8 基准 8.81ms），**计算已不是瓶颈**。R8 §2.4 自己承认 OffscreenCanvas 不减少总计算量，只是解除主线程阻塞；而它带来消息协议、48MB 数据传递（无 COOP/COEP 就 postMessage 拷贝）、不支持时的降级路径三重复杂度。R8 §4.2 结论原文：「锦上添花而非救命」。若真要改善平移手感，优先做 R8 §2.5 离屏预渲染 + `drawImage`（中成本），比 Worker 更贴痛点。

### 4.4 区间统计放前端还是后端

- **选项 A**：前端本地算（R7 §3.5，`statRange` 纯 JS 单次扫描，拖动即时刷新）。
- **选项 B**：后端 `/api/measure?window=[s,e]`（R10 §3 #3 推荐统一口径，§6.1 实测小区间 1–3ms、全量 400–800ms）。
- **建议**：**A 为主、B 兜底与校验（混合方案），不是二选一**。
- **理由**：R7 的理由不可替代——数据已在前端内存，拖动 A/B 时每次 HTTP+JSON 的延迟与抖动不可接受；而 R10 的理由也成立——口径统一和「导出/深分析」需要后端。具体分工：拖动中前端算（可 rAF 节流 + `requestIdleCallback` 分片），落定后与后端同 window 交叉校验（R7 S5 要求 duty 在 ±1e-6 内一致），导出走后端。**注意口径坑**：后端 `min_pulse/max_pulse` 是样本数，前端展示要 ×(1/rate) 才对齐（R7 §4.5 #7）。

### 5.2 需实测验证才能采信的结论

1. **R7 全部数值**：`48e6 样本单通道 <200ms`、标签间距公式、ΔT 示例、8 条冲突场景，都是设计值，必须在目标机 Chrome 逐条跑验收 T1–T5/A1–A5/S1–S5/I1–I3。

6. **R9 私有格式与压缩比**：`.sal` ZIP+parquet 是社区观察；deflate 2:1 是经验值，实际取决于翻转率。
7. **R10 性能与依赖**：全量 8 通道 400–800ms 为估算；`.mat` 导出需 `scipy`，属**新增依赖，须先获授权**，否则该 API 暂缓。

### 5.3 可直接用的结论

1. **R2 的时间轴刻度算法**（采样周期取整 + `boundingRect` 实测文本宽度 + 双阈值次标签）与缩放底数 1.5+offset 补偿公式——源码级，照抄即可。
2. **R6 的硬件边界**（无 ADC、无硬件触发、8 通道、24MHz 上限）——实测+源码，可直接写进用户文档管理预期。
3. **R8 阶段 1 的 Uint32 批量 min/max**——已落地并实测 6.2ms，不必重做；DPR「先设宽高再 scale」的坑可直接采用。
4. **R9 的 `.sr` v2 格式细节与 VCD 合规 8 项检查**——一手抓取，可直接作为会话格式与导出自检依据。
5. **R10 的 API 差异清单、window 参数验证结论、前后端归属判断表**——实读代码得出，可直接作为后端改造规格。

7. **R1/R3 的「功能存在性」判定**（哪些官方有、哪些文档未提及）——可用于第 1 节对照表的覆盖度标签，但不能外推到交互细节。

## 6. 给下一个人的四条路

### 6.1 只想「用起来」——什么都不用做

exe 已经能用：采集（24MHz 满速）、8 通道波形、缩放平移光标、时间轴自动单位、4 个解码器、测量侧栏、CSV/VCD/二进制导出全都在。直接双击运行，不需要读本篇。

### 6.2 想「补功能」——按 P0 做三件事

1. **AB 区间标记 + 区间统计**（5h，R7 现成设计，分 4 阶段验收）。这是用户点名且唯一未交付的诉求。
2. **解码器参数自声明 schema**（6h，地基，先于任何新解码器）。
3. **区间解码 window + 结果分页**（2h，后端 `/api/decode` 切片+limit/offset，约 25 行）。

做完这三件，再按 2.2 顺序取第 4 项会话保存。

### 6.3 想「做产品」——补的是「工作状态不丢」和「错误可解释」

- **会话管理**：保存/加载（`.lcaps` ZIP）、采集历史列表、自动保存与启动恢复、命名/标签/备注（R9 §4 的 P0/P1）。
- **更多解码器**：schema 就位后按 R4 顺序加 1-Wire/PWM/I2S/Manchester/IR NEC。
- **错误处理**：R10 缺口 #3——409 细分 `BUSY/OCCUPIED/NOT_READY/NO_DEVICE` 子码，让前端能自动重试而非靠中文字符串猜。
- **磁盘治理**：R10 缺口 #4——`register` 超 20 条 `popitem` 只丢元数据不删磁盘文件，每次 48MB 累积无界，必须配配额与清理。
- **精致度**：dark/light + 中英 + 快捷键表 + 高 DPI SVG（R2 §11）、VCD 合规化（R9 §3）、全功能演示模式（R5 §6 #5）。

### 6.4 想「继续逆向」——还剩什么没逆

- **触发寄存器协议**：R6 §1.4 列的四步——触发类型寄存器、通道掩码、边沿/电平条件、预触发深度的字节格式与混淆算法；抓包对比 + 施加已知边沿验证固件是否实现。
- **`.logicdata` / `.sal` / `.pvs` 格式**：R9 确认三者**均无公开文档**，只能做合规的逆向工程（`.sal` 社区观察为 ZIP+parquet，不可当事实）。
- **FX2 固件是否阉割触发**：即便逆出命令，也要验证克隆固件真的实现了寄存器；不实现则回到软件触发。
- **硬件边界之外**：>8 通道需 PD0-PD7 额外引脚与不同板卡，>24MHz 受 24MHz 晶振与 8051/FIFO 带宽硬限——这两项属于换硬件，不是继续逆向能解决的。

| **R8 Canvas 性能** | Node 基准四算法对比 + 三阶段策略 | Uint32 批量 min/max 8.81ms（已落地 6.2ms）；OffscreenCanvas 是锦上添花不是救命；ImageData 直写不采用 |
| **R9 会话/导出** | `.sr` v2 一手规范 + 8 种导出对比 | 唯一有权威规范的是 `.sr`，但它是交换格式不是完整会话；选 ZIP `.lcaps`，默认 store；VCD「能导出≠合规」 |
| **R10 后端 API** | 实读 735 行 server.py，10 条差异 + 10 条缺口 | 最要紧：`decode` 加 window、加 `limit/offset` 分页、409 细分 `code`；`.mat` 需 scipy 属新增依赖须授权 |
