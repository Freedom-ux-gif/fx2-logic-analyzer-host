# H3 逆向方法

> 面向想继续深挖或复现这套逆向的工程师。
> 本篇的重点不是"这次做了什么"，而是"遇到类似目标时应该怎么做"。
> 所有推断均标注置信度；未经动态验证的结论不写成定论。

## 0. 本篇能学到什么

这是一篇**方法论手册**，不是项目流水账。读完你应该能在没有现成脚本的情况下，独立对一个"磁盘加密、无源码、有开源参考"的 Windows 二进制完成同类逆向。

核心可迁移的七条：

1. **磁盘高熵不等于不可分析**——先问"运行时会不会解密"，再下结论（见 1.2、5.1）。
2. **元信息比反汇编快 100 倍**——源文件名、类名、日志消息先挖，再谈代码（见 1.3）。
3. **三方对撞才叫确认**——单一来源的结论，哪怕再合理也可能是错的（见 1.4）。
4. **证伪和证实同等重要**——每排除一条路都记录"为什么排除 + 证据"（见 1.5、第 4 章）。
5. **不注入的内存读取是首选**——`ReadProcessMemory` 不会让目标察觉，frida 注入会把目标搞崩（见 2.2）。
6. **capstone 的 `disasm()` 会静默停止**——必须逐字节重试才能达到 99% 覆盖（见 2.4）。
7. **状态串联是混淆器的常见陷阱**——看到 `movzx edi,cl` 这类"保存上一字节"的指令就要警惕（见 3.1、第 7 章）。

**怎么用这篇**：第 1 章是原则，第 2 章是可照抄的流程，第 3 章是这些原则的真实案例，第 4/7 章是别人踩过的坑（帮你跳过），第 5 章是决策树，第 6 章是工具速查。

## 1. 方法论

### 1.1 判断目标是否加密（三步法）

**通用做法**：拿到一个可疑二进制，按顺序做三项检查，任何一项异常都进入"加密 PE 处理流程"。不要跳步，也不要只看其中一项就下结论。

| 步骤 | 做什么 | 判据 | 本次结果 |
|---|---|---|---|
| ① 算熵 | 对每个 PE 段算 Shannon 熵 | 段熵 **> 7.9** 视为可疑 | `.text`=7.995、`.rdata`=7.867（高） |
| ② 看字符串 | 在 `.rdata` 找可读字符串 | 连 OpenSSL 版本号都没有 → 加密 | 磁盘上无可读串（高） |
| ③ 试反汇编 | 用 capstone 反汇编入口点前几条 | 不是合法指令序列 → 加密/混淆 | 0 条有效指令（高） |

**方法论提炼**：
- 熵阈值 7.9 是经验值，不是数学定理。接近 8.0 的段几乎必然是加密或压缩数据，因为自然代码的熵通常在 5–7。
- 字符串检查要找"一定会出现"的基准串，例如 C++ 程序的 `MSVCP140.dll`、加密程序的 OpenSSL 版本串。连基准串都没有，说明数据被加密了。
- 反汇编检查只需看前几条指令。合法入口点通常是 `push rbp / sub rsp,xx / mov …` 这类序言；如果反汇编器报无效指令或输出乱码，就是强信号。

**置信度说明**：三步法本身是可靠的启发式（高）；但"熵高"只能证明"磁盘上的字节不可读"，不能证明"静态不可分析"——这正是下一节要纠正的误判。

### 1.2 加密 PE 的处理流程

**核心原则**：高熵只说明磁盘上的字节被加密，不说明运行时没有解密。务必把"磁盘视图"和"内存视图"分开看待。

```
发现高熵 → 不要下结论"不可分析"
        → 想"运行时会不会解密"
        → 用 ReadProcessMemory（不注入）dump 解密镜像
        → 比对内存熵 vs 磁盘熵
        → 熵降了就说明成功，进入正常反汇编流程
```

**本次实测对照**（可信度：高，来自 `dump_rpm.py` 的逐段输出）：

| 段 | 磁盘熵 | 内存熵 | 磁盘反汇编 | 内存反汇编 |
|---|---|---|---|---|
| `.text` | 7.995 | 6.473 | 0 条 | 99% 覆盖（517 万条） |
| `.rdata` | 7.867 | 6.462 | 无字符串 | OpenSSL 等全部可读 |

**方法论提炼**：
- dump 出的镜像要保持原 PE 段布局，这样反汇编器里的地址与运行期模块地址一致，后续所有 RVA 都能直接对照。
- "熵是否下降"是 dump 成功的判据，不需要先理解加密算法。只要熵降了，就说明拿到了明文视图。
- **教训**：最初的判断"熵 8.0 = 静态不可分析"是错的，错在只看了磁盘文件。以后遇到高熵 PE，第一个问题永远是"运行时是否解密"。

### 1.3 元信息优先原则

**通用做法**：在写任何反汇编脚本之前，先把二进制当文本挖一遍。字符串里的源文件名、类名、日志消息，能直接告诉你模块结构，比逐条读汇编快两个数量级。

**为什么有效**：C++ / Qt 程序会把调试与日志信息编译进二进制：
- `__FILE__` 宏 → 完整的源文件路径；
- Qt 的日志宏 / `Q_OBJECT` 元对象 → `Class::Method` 形式的字符串；
- 这些字符串即使在加密镜像里也可能残留在未加密的数据区（本例在 dump 后的镜像里完整可读）。

**本次产出**（可信度：高，用字符串提取工具在解密镜像上实测）：
- 101 个源文件名，例如 `LogicDevice.cpp`、`BasicCryptoCommands.cpp`、`WindowsUsbDevice.cpp`、`Logic2FpgaDevice.cpp`；
- 453 个 `Class::Method` 字符串。

**方法论提炼**：
- 源文件名直接暴露模块划分：看到 `BasicCryptoCommands` 就知道认证逻辑在哪，看到 `WindowsUsbDevice` 就知道 USB 写在哪——省掉大量猜谜。
- 对于 Qt / MFC / C++ 程序，优先搜 `::` 模式；对于 Go / Rust 程序，优先搜包路径与符号名。每种语言都有"必然泄露的元信息"。
- 挖到的字符串要保留为"定位锚点"，下一步用交叉引用把它们对应到代码（见 2.4）。

### 1.4 三方交叉验证

**通用做法**：任何关键结论，至少有 **两个独立来源** 对撞才能采信。单一来源的结论一律标为"待验证"。

**为什么**：本次一度认定数据在 `0x81`，实际在 `0x82`——单一来源（抓包的表象）导致误判。命令格式之所以敢确认，是因为三条独立证据链全部吻合：

| 结论 | 来源 1 | 来源 2 | 来源 3 | 结果 |
|---|---|---|---|---|
| 采样率命令 `{0x01, 48MHz/rate−1}` | 反汇编某函数 | 开源 `keesj` 硬编码表 | sigrok 采样率文档 | 10 档全中（2MHz 差 1，实现取舍不同） |
| 首字节 `0xd5` = 新固件签名 | 混淆器复算 `enc(0x01)=0xd5` | sigrok 文档 | 抓包应答 `d5 e2` | 一致（高） |
| 明文 `7d 55` → 线上 `61 d4` | 混淆器正向 `enc` | 混淆器逆向 `dec` | 官方抓包 | 逐字节一致（高） |

**方法论提炼**：
- "独立来源"指的是**获取途径独立**，不是同一份数据的不同表述。反汇编、开源实现、实测抓包是三种独立途径。
- 对撞时出现不一致（如 2MHz 差 1）不要强行抹平；如实记录差异，并说明"实测时两个值都试"的应对。
- 单一来源的结论（如 `0x58` 是"查询固件签名"）即使合理，也只能标中等置信度。

### 1.5 证伪比证实更重要

**通用做法**：每排除一条路，都记录三件事——**尝试了什么、得到什么结果、为什么排除**。这份清单能防止后续迭代时重复踩同一个坑。

本次排除了 5 条主要路线（详见第 4 章），每条都有实测数据支撑。经验法则：

- 一个"看似可行"的路线，如果实测出现"服务端 0 字节发出""22 个前缀只有 2 个有效"这类数字，就是强证伪信号，应立即止损转向。
- 证伪结论要区分"这条路走不通"和"这条路当前条件下走不通"。后者要写清楚"若要再试需要什么条件"（见第 4 章最后一列）。
- "硬件加密认证不存在"这类证伪同样有价值：它把精力从"破解芯片"重新引导到"分析上位机协议"。

**方法论提炼**：证伪清单应作为交付物的一部分，而不是遗忘在聊天记录里。交接给下一个工程师时，它能直接省掉几天的重复劳动。

## 2. 可复现的逆向流程

以下五步按顺序执行，前一步失败才进入后一步。每步都给出可复制的命令或脚本骨架（每段 ≤ 20 行）。

### 2.1 第 1 步：静态侦察

**目的**：判断目标是否加密，决定后续走"内存 dump"还是"直接反汇编"。

**操作**：算熵、找字符串、试反汇编。把三项结果填进 1.1 的表格。

**脚本 A：逐段算熵**（可复制运行）
```python
# 用法: python -I entropy.py Logic.exe   —— 段熵 >7.9 视为可疑
import collections, math, sys, struct
def H(b):
    if not b: return 0.0
    c=collections.Counter(b); n=len(b)
    return -sum(v/n*math.log2(v/n) for v in c.values())
raw=open(sys.argv[1],"rb").read()
pe=struct.unpack_from("<I",raw,0x3C)[0]
n=struct.unpack_from("<H",raw,pe+6)[0]
os=struct.unpack_from("<H",raw,pe+20)[0]
off=pe+24+os
for _ in range(n):
    nm=raw[off:off+8].rstrip(b"\0").decode("latin1")
    vs,va,rs,rp=struct.unpack_from("<IIII",raw,off+8)
    if rs: print(f"{nm:8s} disk_H={H(raw[rp:rp+rs]):.3f}")
    off+=40
```

**脚本 B：字符串 + 入口反汇编合法性**（可复制运行）
```python
# 用法: python -I probe.py Logic.exe —— 基准串 + 入口前几条指令
import re,sys,struct
from capstone import Cs,CS_ARCH_X86,CS_MODE_64
b=open(sys.argv[1],"rb").read()
print("OpenSSL:", re.findall(rb"OpenSSL[\w .-]{0,30}",b)[:3])
pe=struct.unpack_from("<I",b,0x3C)[0]
ep=struct.unpack_from("<I",b,pe+24+16)[0]      # 入口 RVA
md=Cs(CS_ARCH_X86,CS_MODE_64)
code=b[ep:ep+24]   # 仅当文件偏移==RVA 时可直接用；否则先定位所属节
for i in md.disasm(code, image_base + ep):
    print(f"0x{i.address:x}: {i.mnemonic} {i.op_str}")
```

**判读**：如果三项都异常（熵高、无基准串、反汇编乱码），直接进入 2.2。

### 2.2 第 2 步：内存 dump（静态失败时）

**目的**：拿到运行时的解密镜像。

**为什么用 `ReadProcessMemory` 而不是 frida 注入**：frida 在一个会话里创建多个脚本会导致目标进程 tear down（崩溃）；`ReadProcessMemory` 不需要向目标注入任何代码，只以 `PROCESS_VM_READ` 权限读取，目标进程保持正常运行。这是"最小侵入"原则的体现——**能只读就不注入**。

**核心逻辑**（工具脚本 `dump_rpm.py` 未随本仓库分发；下面是关键骨架，照此可实现等价工具）：
```python
# 不注入，只读取目标进程内存；保持 PE 布局，地址与运行期一致
disk=open(EXE,"rb").read(); secs,ep=parse_sections(disk)
p=subprocess.Popen([EXE]); time.sleep(8)        # 等它完成运行时解密
h=k32.OpenProcess(0x0400|0x0010,False,p.pid)    # QUERY_INFO|VM_READ
base,size=module_base(p.pid,"Logic.exe")        # Toolhelp32 快照找模块基址
out=bytearray(disk)
for name,va,vs,rp,rs in secs:
    if not rs: continue
    mem=read_mem(h,base+va,rs)                  # ReadProcessMemory
    out[rp:rp+rs]=mem
    print(name,f"H {H(disk[rp:rp+rs]):.3f} -> {H(mem):.3f}")
open("decrypted_image.bin","wb").write(out)      # 布局不变，RVA 全部沿用
```

**验收判据**：输出里每一段的熵必须明显下降。本次 `.text` 7.995→6.473。若熵没降，说明没等到解密时机，增大 `--wait` 重试。

**用法**（示意，工具未随仓库分发）：`python -I dump_rpm.py --out <镜像>.bin --wait 8`

### 2.3 第 3 步：字符串情报提取

**目的**：从解密镜像里挖出源文件名、类名、日志消息，建立模块地图。

**工具**：`intel.py`（本项目的辅助脚本，**未随本仓库分发**；功能很简单，按下述输出规格可自行实现）

**用法与输出样例**：
```bash
python -I intel.py <解密镜像> --sources
# 泄露的源文件路径：101
#   LogicDevice.cpp
#   BasicCryptoCommands.cpp
#   WindowsUsbDevice.cpp
#   Logic2FpgaDevice.cpp

python -I intel.py <解密镜像> --classes
# Class::Method 字符串：453 个唯一值
# ## WindowsUsbDevice (...)
# ## BasicCryptoCommands (...)
```

**方法论提炼**：先用 `--sources` 看模块全貌，再用 `--classes` 定位具体类，最后用 `--strings PATTERN` 搜关键词（如 `sampl`、`crypto`、`Write`）拿到字符串在镜像里的文件偏移——这些偏移是下一步交叉引用的输入。

### 2.4 第 4 步：定位关键函数

**目的**：把字符串锚点对应到代码地址。

**（a）RIP 相对寻址交叉引用**：x86-64 下，代码通过 `disp32 = 目标地址 − (指令地址 + 指令长度)` 引用数据。暴力扫描 `.text` 里所有指令，重算其 RIP 目标，命中目标字符串 VA 的即为引用点。

**骨架**（前置变量 `pe/f/md/IMG/targets/hits` 自行定义；完整实现思路见 `逆向方法论/03_工具说明.md`）：
```python
for s in pe.sections:
    if s.Name.rstrip(b"\0")!=b".text": continue
    off,sz,va=s.PointerToRawData,s.SizeOfRawData,s.VirtualAddress
    seg=f[off:off+sz]; i=0
    while i<len(seg)-16:
        for ins in md.disasm(seg[i:i+16],IMG+va+i):
            # 精确 RIP 目标 = ins.address + ins.size + disp32
            if rip_target(ins) in targets:           # 命中字符串 VA
                hits.append((ins.address-IMG,ins.mnemonic,ins.op_str))
            i+=ins.size; break
        else:
            i+=1                                    # 关键：不可解码就前进 1 字节
```

**（b）必须逐字节重试的坑**：capstone 的 `disasm()` 生成器遇到无效字节会**静默停止**。直接 `for ins in md.disasm(seg,...)` 只能覆盖约 1629 条指令；改成"解码失败就 `i+=1` 重试"后达到 **517 万条、99% 覆盖**。这是本流程最关键的技术细节——**覆盖率不足时，先怀疑反汇编器的停止行为，而不是怀疑目标**。

### 2.5 第 5 步：反汇编分析关键逻辑

**目的**：在已定位的函数里读懂算法。

**（a）用 `.pdata` 框定函数边界**：PE 的异常表 `.pdata` 里每项记录 `{起始RVA, 结束RVA, 展开信息}`，按起始 RVA 递增有序，可二分查找：

```python
def find_func(addr,ranges):     # ranges=[(start,end),...] 按 start 排序
    lo,hi=0,len(ranges)-1
    while lo<=hi:
        mid=(lo+hi)//2; s,e=ranges[mid]
        if addr<s: hi=mid-1
        elif addr>e: lo=mid+1
        else: return (s,e)
    return None
# 用途：字符串 xref 落在某地址 → 用 .pdata 框定边界 → 全量反汇编该函数
```

**（b）真实案例：从字符串到算法**。先用 `intel.py --strings StartSampling` 拿到字符串偏移，交叉引用定位到某采样函数后，全量反汇编 200 条指令，找到三条关键指令：`mov eax, 48000000`（=48,000,000）、`div edi`（除以采样率）、`dec r14b`（减一）
- → 得出 `divider = 48000000/rate − 1`（可信度：高，算术直接可读）。

继续追命令构造点，看到 `mov byte [rsp+0x40],1` 与 `mov [rsp+0x41],al`，确认命令格式 `{0x01, divider}`、长度 2（可信度：高）。

**方法论提炼**：先定位函数边界，再全量反汇编，不要只看零散几条。算法往往分散在函数首尾的常量加载与算术指令里。

## 3. 本次案例（作为案例，不是流水账）

### 3.1 混淆机制：结论与验证向量

本节仅给出**结论与可验证的规格**，不记录推导过程。任何读者拿下面的实现 + 验证向量，都能独立复现该算法并自校验。

```python
def obfuscate(plain):
    out, A, B = [], 0x54, 0x9B
    for p in plain:
        t = A ^ p
        t ^= 0x2B
        t = (t - 5) & 0xFF
        t ^= 0x35
        t = (t - 0x39) & 0xFF
        t ^= B
        t ^= 0x5A
        t = (t + 0x50) & 0xFF
        t ^= 0x38
        t = (t - 0x45) & 0xFF
        out.append(t)
        B, A = p, t
    return bytes(out)
```

**状态机语义**：初值 `A=0x54`（上一密文字节）、`B=0x9B`（上一明文字节）；每字节做 10 步变换，每步 `& 0xFF`；状态更新 `B, A = p, t`。因此算法**有状态**——同一明文在不同位置会得到不同密文，不能用无状态替换表代替。

该函数对应原厂程序中某 495 字节函数的等价实现，本项目给出的是独立重写版本，未复制原厂代码。

| 明文（hex） | 加密后（hex） | 验证来源 |
|---|---|---|
| `01` | `d5` | sigrok 文档「新固件首字节 0xd5」 |
| `01 03` | `d5 e2` | 设备对 `0x58` 命令的应答比对 |
| `01 05` | `d5 d4` | 反汇编复现，与设备行为一致 |
| `01 2f` | `d5 8e` | 实测：明文 `012f` 不出数据，密文 `d58e` 立刻出数据 |
| `7d 55` | `61 d4` | 官方抓包 |
| `01 0b` | `d5 da` | 4MHz 采集实测：`--rate 4000000` 时打印 `plaintext 010b -> wire d5da` |

### 3.2 命令格式确认

反汇编该命令构造点的三条指令：
```asm
mov byte [rsp+0x40], 1     ; buffer[0] = 0x01 硬编码
mov [rsp+0x41], al         ; buffer[1] = divider-1
mov r9d, 2                 ; 长度 2
```

**与开源项目对撞**（不是在照抄，而是独立验证）：
- `keesj/saleae-logic-libusb` 的硬编码表；
- sigrok 文档的 `48MHz/rate−1` 表述；
- 本地抓包的 10 档采样率全部对上（2MHz 差 1，实现取舍不同，实测两个值都试）。

> **可迁移经验**：开源实现给你的是"假设"，反汇编和抓包给的是"证据"。三者对撞一致才升级为结论；不一致的地方如实保留。

### 3.3 SDK ABI 索引（`01_sdk/`）

- 272 个导出**全部是标准 MSVC 修饰名，无混淆**（可信度：高，`dump_exports.py` 实测）。
- 24 个类；插件三入口 `CreateAnalyzer` / `DestroyAnalyzer` / `GetAnalyzerName`（可信度：高）。

> **可迁移经验**：先判断目标是否暴露了标准 ABI。若有，导出表就是一份"免费头文件"，能直接恢复类与方法签名——这比从汇编里反推对象布局可靠得多。修饰名若未混淆，用 `demangle` 即可读。

## 5. 方法论总结（决策树）

### 5.1 遇到加密 PE 怎么办

```
拿到二进制
├─ 熵 >7.9 且无基准字符串？
│   ├─ 否 → 正常静态分析
│   └─ 是 → 问"运行时会解密吗？"
│        ├─ 能运行 → ReadProcessMemory dump（不注入）
│        │          → 比对熵 → 下降则进入静态分析
│        └─ 不能运行 → 考虑动态调试/沙箱，或换样本
└─ 反汇编覆盖率低？
    └─ 先查 capstone 是否遇到无效字节停止 → 逐字节重试
```

### 5.2 只有一个二进制没有源码怎么办

1. **先挖元信息**：字符串、符号、导出表、RTTI、调试路径——任何"作者无意留下的东西"。
2. **建模块地图**：用源文件名/类名把二进制切成可理解的单元。
3. **从锚点进代码**：字符串交叉引用 → `.pdata` 定边界 → 全量反汇编。
4. **只还原够用的部分**：目标是协议/算法，不必把整个程序逆完。
5. **标注置信度**：能确定的写"高"，靠推断的写"中/低"，不确定的写"证据不足"。

### 5.3 有开源参考实现时怎么用

**原则：对撞验证，不是照抄**。开源项目提供"假设"和"坐标"，你的反汇编/抓包提供"证据"。用法：
- 把开源里的常量/公式当作待验证假设，逐条去反汇编和抓包里找对应证据；
- 三者一致 → 升级为结论；三者冲突 → 如实记录差异（如 2MHz 差 1、数据在 `0x81` vs `0x82`）；
- 注意开源项目可能描述的是**不同固件/不同硬件版本**，不能直接套用。

### 5.4 什么时候该放弃一条路

出现以下信号就止损转向，不要在一条路上耗到底：
- **零输出**：投入明显成本后仍是"服务端 0 字节""0 处命中""0 条指令"——这是强证伪信号。
- **命中率极低**：盲猜 22 个只有 2 个有效，说明缺的是信息而不是运气，应回去补情报。
- **前提不成立**：确认硬件认证不存在后，继续研究"破解芯片"就是浪费。
- **边际收益递减**：静态反汇编已把协议讲清楚，剩下 5% 需要动态调试时才考虑上重型工具（如 Ghidra）。
- 放弃时按第 4 章格式记录：尝试、结果、结论、**若要再试需要什么**。

## 7. 踩过的坑（按严重程度排序）

1. **磁盘高熵就断言"静态不可分析"**（最严重，差点放弃）——只看了磁盘文件。正解：先问运行时是否解密，用 RPM dump 后覆盖率 0%→99%。
2. **混淆器"独立变换"假设**——多字节变换以为每字节用同一初值，结果第二字节全错。正解：看到 `movzx edi,cl` 这类保存上字节的指令就要识别状态串联。
3. **capstone `disasm()` 遇无效字节静默停止**——覆盖仅约 1629 条。正解：解码失败 `i+=1` 逐字节重试，达到 517 万条。
4. **frida 注入导致目标崩溃**——一个会话建多个脚本，目标 tear down。正解：只读场景优先 `ReadProcessMemory`，不注入。
5. **单一来源认定数据在 `0x81`**——实际开源都说 `0x82`，本机端点表是 `01/81/02/04/86/88`。正解：三方对撞，差异如实标注待实测。
6. **`0x61 = 0x01 ^ 0x60` 的臆测**——全镜像扫描无 `xor al,0x60` 形式的常量混淆，排除（低置信度）。正解：猜想要拿全镜像扫描去证伪。
7. **盲猜命令字节**——22 个前缀只有 `0x58`/`0x61` 有效。正解：先反汇编拿命令格式，别靠枚举碰运气。
8. **端点 alt setting 0 导致所有 pipe 操作失败**——`WinUsb_Initialize` 默认停在 alt 0（0 个端点），任何操作返回 `ERROR_INVALID_PARAMETER(87)`，曾误判"设备坏了"。正解：先切 alt setting 1。
9. **自测全过不等于正确**——`test_decoders.py` 报"ALL PASSED"，独立复跑发现 4 处实际错误（UART 位漂移、I2C 位序反、SPI 生成器崩）。正解：验收必须用外部可复现的具体数值，不接受笼统通过声明。
10. **sigrok 公式直接套用**——文档那列其实是加密后字节。正解：先解码到明文空间再比对，区分"线上值"与"内部值"。

> 排序依据：是否会导致"整个方向判错"或"浪费数天"。前三条都曾让分析跌入死胡同。
