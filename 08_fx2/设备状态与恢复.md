# 设备状态与恢复步骤

> 最后更新：2026-11-24 22:32

## 当前状态：需要物理拔插

```
Get-PnpDevice → Status = OK, Present = True
但所有 USB 操作失败：
  写 EP 0x01        → 121 ERROR_SEM_TIMEOUT
  控制传输 GET_DESCRIPTOR → ERROR_GEN_FAILURE（设备已断开）
```

设备在系统里"看起来在"，但**固件已经挂起**，不再响应任何端点。
这是 FX2 芯片在错误状态下运行时的典型表现——主机侧无法复位，只能断电重连。

## 恢复步骤（按顺序）

1. **物理拔掉 USB 线，等 5 秒，再插回**
2. 确认设备出现在系统里：
   ```bash
   powershell -NoProfile -Command "Get-PnpDevice -PresentOnly | Where-Object {$_.InstanceId -match '0925'} | Format-Table Status,FriendlyName"
   ```
   应显示 `Status=OK`
3. **先跑一次 Logic.exe**（重要，见下节），然后关闭它
4. 跑采集测试：
   ```bash
   cd 08_fx2
   python -I capture_fx2.py --rate 1000000 --seconds 3 --out wave.bin
   ```

## 为什么必须先跑一次 Logic.exe

实测对比：

| 场景 | EP1 OUT 写 | 结果 |
|---|---|---|
| Logic.exe 刚跑过、然后关闭 | 成功 | 握手成功，读回 `0x40` / `616f91d7e44946ae` |
| 冷启动后直接用自己的代码 | 121 超时 | 设备不响应 |

推断（未验证）：**设备的 FPGA 采集引擎需要官方软件初始化**。FX2 刚上电时只有 USB 固件在跑，
采集引擎还没配置。官方软件启动时会切到 alternate setting 1 并下发采集参数，之后端点才真正可用。
我们自己的代码目前只做了 `alt setting` 切换，没有下发采集参数。

## 反汇编已找到缺失的那一步（重要）

`Logic.exe` 里有一个类叫 **`Logic2FpgaDevice`**（源文件 `Logic2FpgaDevice.cpp`），
它的存在说明本机这一类设备在开始采集前必须**把采集参数下载到 FPGA**：

```
Logic2FpgaDevice::SetCaptureParameters
   "setting capture settings"
   "reading back capture settings"
   "Capture parameter failed to download to device"
Logic2FpgaDevice::InitAdc
   "digital gain out of range."
   "invalid mix ratio."
```

关键证据：`SetCaptureParameters` 的实现在 RVA `0x2efe50`–`0x2f04xx`，
在 `0x2f009c` 处调用 `0x322e80`（参数打包器），传入 **10 个参数**：

```asm
0x2f009c call 0x140322e80
    ecx = r15d   ; 数字通道计数
    edx = r12d   ; 数字通道位掩码
    r8d = r13d   ; 模拟通道计数
    r9d = r14d   ; 模拟通道位掩码
    [rsp+0x20] = 0x20 或 0x10   ; ← 深度位宽（16bit 还是 32bit）
    [rsp+0x28] = 0xc            ; 12
    [rsp+0x30] = &[rbp-0x64]    ; 输出：mix rate 分子
    [rsp+0x38] = &[rbp-0x68]    ; 输出：mix rate 分母
    [rsp+0x40] = &[rbp+4]
    [rsp+0x48] = &[rbp]
```

随后在 `0x2f00a1` 检查两个输出值必须 `<= 0xFF`，超过就报错——
这与 `DeviceHelpers.cpp` 里的 `DeviceCalculateMixRate` / `Invalid multiplier: %d` 对应。

**所以完整的启动流程应该是至少三步，不是一步：**

1. 切 alternate setting 1（已实现，`winusb.py::_select_endpoint_alt_setting`）
2. **下发采集参数包**（`SetCaptureParameters`，尚未实现 ← 当前缺的就是这一步）
3. 发 `{0x01, sample_delay}` 开始流式传输（已实现，`capture_fx2.py::start_stream`）

第 2 步的参数包格式还没完全还原（打包器 `0x322e80` 内部还有分支，
包括 16-bit/32-bit 深度、`cmp eax,0xa` 的通道类型判断等）。
**这是明天最值得继续挖的地方**——一旦解出来，采集就能通。

另外注意：`Logic.exe` 安装目录里**没有任何 `.bin`/`.rbf`/`.bit` 文件**，
说明比特流（如果有）是编译进 exe 的 14MB 第二个 `.text` 段里。
但 `Logic2FpgaDevice` 这个类名暗示它的 FPGA 是**通过参数寄存器配置**，不是下载比特流。


从原厂程序里挖出的字符串（分析结论见 [`逆向方法论/`](../逆向方法论/00_总览.md)，原始反汇编未随本仓库分发）：
- `LogicGraduateDevice::LoadBitstream` / `Logic Graduate Bitstream failed to download.`
- `Logic16Device::LoadBitstream`
- `LogicDevice` 的构造里有 `Incorrect endpoint count %u` 检查

## 另一件重要的事：实际端点表和开源文档不一致

实测本机（`winusb.py` 的 `list_pipes()`）得到的端点：

```
0x01  Bulk  maxpkt=512   ← 命令 OUT
0x81  Bulk  maxpkt=512   ← 命令应答 IN
0x02  Bulk  maxpkt=512
0x04  Bulk  maxpkt=512
0x86  Bulk  maxpkt=512
0x88  Bulk  maxpkt=512   ← 可能是真正的数据 IN（不是 0x82）
```

**注意：没有 `0x82`。** 而两个开源实现都说数据在 `0x82`：

- `keesj/saleae-logic-libusb`：`STREAMING_DATA_IN_ENDPOINT = 0x82`
- `sigrok/fx2lafw`：`2 | LIBUSB_ENDPOINT_IN` = `0x82`

本机是 **`0x88`**。原因推测：克隆板的 FPGA 配置和原厂不同，端点布局随之不同。
**这一点必须在设备恢复后实测确认。**
