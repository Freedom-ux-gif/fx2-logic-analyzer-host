# 会话管理与导出格式调研

> 目标：为我们现有的逻辑分析仪上位机补齐「采集会话管理」与「数据导出格式」能力。
> 现状：采集数据为裸字节 `capture_YYYYmmdd_HHMMSS_<rate>.bin`（每字节 8 通道），导出仅 CSV(changes)/VCD/二进制，无会话、无历史、无标注。
> 硬件上限：24MHz × 2s = 4800 万样本 × 1B × 8 通道 = 48,000,000 B ≈ 45.8 MiB；会话容器必须能装下该量级。

## 1. 会话文件格式对比

### 1.1 sigrok .sr（v2）

来自 sigrok wiki 的一手事实（已抓取原文）：

- **容器**：标准 ZIP 文件，推荐扩展名 `.sr`。概览页明确标注 Compression = ZIP。
- **必备条目**：
  - `version`：ASCII，单行整数，当前为 `2`；每次格式变更递增。
  - `metadata`：ASCII，INI 风格语法。
- **metadata 语法细节**：
  - 行尾可为 `\r`、`\n`、`\r\n`、`\n\r`；
  - 空行与以 `#` 开头的行忽略；
  - 段名形如 `[<sectionname>]`，括号内不允许空白；
  - 段名允许字符：A-Z/a-z/0-9/空格；键允许字符：A-Z/a-z/0-9/空格/减号 `-`；
  - `key=value`，等号两侧空白忽略；单行最大 4093 字符。
- **metadata 段/键**：
  - `[global]`：`sigrok version`；
  - `[device X]`（X 为设备序号）：`driver`（可选）、`capturefile`、`unitsize`、`total probes`、`total analog`、`samplerate`、`probeX`、`analogX`。
- **采样数据条目**：
  - 逻辑：`logic-1`（单个大文件，**deprecated 但仍支持**）或分段 `logic-1-1`、`logic-1-2`…（多个小文件）；
  - 模拟：`analog-1-<chan>-1`、`analog-1-<chan>-2`…；
  - 均为 ZIP 内二进制文件，wiki **未规定**逐字节布局与单元大小以外的编码。
- **触发位置**：wiki 的 metadata 键列表中**没有**触发位置键（无 trigger 元数据）。
- **解码结果**：wiki 页面**未列出**任何解码结果条目或元数据段 → 不存解码结果。
- **视图状态**：wiki 页面**未列出**缩放/通道显隐/标记等条目 → 不存视图状态（这是社区已知：视图状态不属于 .sr 规范）。
- **元数据里没有通道名**：只有 `probeX`（探针编号/标签），无自由命名通道字段。

结论：.sr 是「采集数据 + 最小元信息」的交换容器，不是完整会话文件；它解决的是「数据不丢」，不解决「工作状态不丢」。

### 1.2 PulseView .pvs

- **无公开文档**：PulseView 官方 wiki 与手册中**未找到** `.pvs` 格式的公开规范。
- 可证实事实：PulseView 是 sigrok 生态的 Qt 图形前端，支持协议解码器、通道组；其原生存档依赖 sigrok `.sr`。
- 推测（**非官方确认**）：社区有时用 `.pvs` 指代 PulseView 的视图/会话状态文件，但**没有可引用的公开格式说明**，本报告不描述其内部字节结构。
- 结论：**无公开文档**，不能作为我们设计的可参考规范，仅作「视图状态需要单独持久化」的需求佐证。

### 1.3 Saleae .logicdata

- **无公开文档**：未找到 Saleae 官方发布的 `.logicdata` 内部结构规范。
- 可证实事实：`.logicdata` 是 Logic（一代）软件的采集数据目录/文件格式，主要用于保存原始采集样本；Saleae 官方曾说明旧 `.logicdata` 可被 Logic 2 导入。
- 内部（目录结构/二进制布局）：**不编造**，标注「无公开文档」。
- 视图状态/解码：无公开资料证实其保存这些，按「未公开」处理。

### 1.4 Saleae .sal

- **无官方公开格式规范**（Saleae 支持页 404，未取得官方文档）。
- 社区逆向/观察（**非官方确认，仅作参考，不作为设计依据**）：`.sal` 表现为 ZIP 容器，内部含 `metadata.json` 以及按通道分片的 parquet 列存文件用于波形/解码数据。
- 由于缺乏官方规范且版本演进可能破坏兼容，本报告**不**对其内部结构下确定性结论，只标注「基于 ZIP+列存的现代化会话容器」这一趋势。
- 可证实事实：`.sal` 是 Logic 2 的工程/会话文件格式，能保存采集、解码器、标记与视图设置（来源于产品行为层面，而非格式文档）。

### 1.5 对比表（容器/压缩/元数据/波形编码/解码结果/文档）

| 格式 | 容器 | 压缩 | 元数据 | 波形编码 | 解码结果 | 视图状态 | 公开文档 |

| sigrok `.sr` v2 | ZIP | ZIP(deflate) | INI：`version`/`metadata`，含 samplerate/probe 等，无触发位置 | 裸二进制字节流（segment 可分段） | 不存（规范未列） | 不存（规范未列） | **有（已抓取，权威）** |
| PulseView `.pvs` | 未知 | 未知 | 未知 | 未知 | 未知 | 疑似用于视图状态 | **无公开文档** |
| Saleae `.logicdata` | 未公开 | 未公开 | 未公开 | 原始样本，未公开 | 未公开 | 未公开 | **无公开文档** |
| Saleae `.sal` | ZIP?（社区观察） | 是?（列存压缩） | JSON?（社区观察） | 列存 parquet?（社区观察） | 能存（产品行为） | 能存（产品行为） | **无官方规范** |

> 关键结论：唯一有权威公开规范的是 `.sr`，但它是交换格式而非完整会话；`.sal` 产品能力最完整但无规范可抄。我们的设计应「借鉴 `.sr` 的容器简洁性 + 补齐视图状态/解码/标注」，走自己的版本化格式。

## 2. 导出格式调研（8 种）

每种给「规范要点 / 实现难度 / 文件体积估算」。难度分为 易/中/难（以我们现有 JS/前端技术栈与裸字节数据为基准）。

### 2.1 VCD（含规范细节验证）

- **规范要点**：IEEE 1364 定义的文本波形格式。结构：`$date`…`$end` → `$version`…`$end` → `$timescale <n><unit>` `$end` → `$scope module …` `$end` → 若干 `$var <type> <width> <id> <name> [$end]` → `$upscope` `$end` → `$enddefinitions` `$end` → 初始化 `$dumpvars` → 逐行时间戳变化点。标量值 `0/1/x/z`，向量值 `b1010`。
- **实现难度**：**易**（我们已有；主要工作是规范合规修正，见第 3 节）。
- **体积估算**：见第 2.1 末与第 3 节公式；48M 样本 8 通道、翻转率 p 时约 `8×48e6×p` 个变化点 × 约 10B/点。

### 2.2 CSV

- **规范要点**：无单一强制标准，RFC 4180 为通用约定（逗号分隔、引号转义、CRLF 行尾）。逻辑分析仪有两种模式：
  - **changes 模式**（我们现有）：每行 `<time>,<channel>,<value>`，只记录跳变；
  - **samples 模式**：每行一个采样点、每通道一列，`t,c0,c1,…,c7`。
- **实现难度**：**易**；加 samples 模式即可，注意 4800 万行会生成数 GB 文件，需警告/分块。
- **体积估算**：changes：`changes × (~25B)`；samples：`48e6 × (1+8×2) ≈ 816 MB`（未压缩纯文本）。

### 2.3 二进制原始

- **规范要点**：我们现有 `.bin`，每字节 8 通道、无头信息；采样率/通道数靠文件名或外部元数据。若要自描述应加文件头（magic + 版本 + 采样率 + 通道数 + 样本数）。
- **实现难度**：**易**（已有）。
- **体积估算**：固定 `样本数 × ceil(通道数/8)` = 48,000,000 B ≈ 45.8 MiB。

### 2.4 MATLAB .mat

- **规范要点**：MAT-file v5 为二进制；Header(128B) + 数据元素（tag: 类型 2B + 字节数 2B/4B）。v7.3 基于 HDF5。逻辑值可用 `uint8` 矩阵 `[samples × channels]`；采样率作为标量变量。
- **实现难度**：**中**（需实现 MAT v5 tag 结构；可用现成库但契约不许新增依赖 → 需手写最小子集，约 1 个元素头结构）。
- **体积估算**：与原始接近，`48e6 + 标签开销` ≈ 45.8 MiB。

### 2.5 NumPy .npy

- **规范要点**：`.npy` = 魔数 `\x93NUMPY` + 版本(1/2/3) + header(长度+Python dict 字面量，描述 dtype/fortran_order/shape) + 原始数据块。`.npz` 是多个 `.npy` 的 ZIP 包（可含波形 + 元数据数组）。
- **实现难度**：**易～中**（header 是文本 dict，手写简单；`.npz` 复用 ZIP 能力）。
- **体积估算**：`.npy` ≈ 48 MB + header 几十字节；`.npz` 压缩后视数据熵，约 24～48 MB。

### 2.6 Wavedrom JSON

- **规范要点**：JSON 描述时序图：`{signal:[{name,wave,bits}],config:{hscale},foot,head}`；`wave` 字符串用字符编码边沿：`0/1` 电平、`l/h` 低/高、`z` 高阻、`u/d` 上升/下降、`=value` 数据、`2..9` 多位。适合文档/网页示意，**不适合 4800 万样本**（本质是压缩成变化序列的示意）。
- **实现难度**：**中**（需把通道变化序列压成 wave 字符串，长序列要分块/采样）。
- **体积估算**：`变化点数 × ~2B`；若先降采样到几千点，则仅数 KB。

### 2.7 PNG 截图

- **规范要点**：PNG（RFC 2083/ISO-IEC 15948）无损压缩位图；zlib/deflate 压缩扫描线，每行前置 filter 字节。由 canvas 直接导出（`canvas.toBlob`）。**不可再导入为数据**，仅用于报告/分享。
- **实现难度**：**易**（canvas 现成能力；需要做离屏高分辨率渲染）。
- **体积估算**：宽度 1600、高度 600、8 通道波形，典型 100KB～1MB，取决于缩放与颜色数。

### 2.8 JSON 结构化

- **规范要点**：无强制 schema，建议 `{format_version, capture:{...metadata...}, channels:[...], changes:[{t,ch,v}], decoders:[...], markers:[...]}`。便于二次开发与 Web API 消费。
- **实现难度**：**易**（但 4800 万变化点 JSON 体积巨大，需限制/分页）。
- **体积估算**：`变化点数 × ~30B`（含键名）；建议只导出选区或降采样，否则可达数百 MB。

## 3. VCD 规范细节验证

逐条列检查项与结论（依据 IEEE 1364 VCD 标准 + 我们实现的已知形态）。我们生成 VCD 时应满足以下 ≥5 项：

1. **`$timescale` 允许值**：标准只允许 `1/10/100 × (s|ms|us|ns|ps|fs)`，共 15 种（常用到 ps；`fs` 为 Verilog-2001 增补）。不得写任意值如 `24MHz` 或非 1/10/100 倍率。
   - 检查：我们输出的是否为上述集合之一（如 `10ns` 对应 100MHz、`1ns` 对应 1GHz）；24MHz 无法精确整除，应取可接受近似（见第 3 项）。
2. **变量标识符字符集**：identifier code 只能是**可打印 ASCII（0x21–0x7E）且不含空格**；应短且唯一（如 `!`、`"`、`#`…或 `a`、`b`）。检查：不得用含空格/非 ASCII/逗号的名称作 id。
3. **时间戳与采样率对齐**：VCD 时间为整数，单位是 `$timescale`。正确做法：`timescale = 1 / samplerate`，则样本 k 的时间戳 = k。24MHz → 1/24e6 ≈ 41.666ns，标准无该值 → 必须二选一：(a) 选 `1ns` 并把样本 k 映射为 `round(k×1000/24)`（会引入舍入抖动）；(b) 选 `10ns` 并按比例记录。我们实现需检查是否做了该映射，而非简单把样本序号当时间戳却声明错误 timescale。
4. **值字符集**：标量只允许 `0/1/x/z`（大小写按工具兼容，通常小写）；向量为 `<width>'b<bits>` 或 VCD 简化 `b<bits>`。检查：不得输出二进制字符串当标量值。
5. **`$dumpvars` 初始化**：`endsdefinitions $end` 后必须用 `$dumpvars` 给所有变量初值，再 `$end`，否则播放器初始态未知。
6. **作用域完整性**：`$scope` 与 `$upscope $end` 必须配对，声明段在 `$enddefinitions $end` 之前。
7. **换行与时间递增**：每个时间戳单独一行（`#[integer]`），后续变化点可省略时间戳；时间戳必须单调不减。
8. **字符集/编码**：VCD 为纯 ASCII（header 中 `$date`/`$version` 用可打印字符）；UTF-8 通道名可能不兼容老工具，建议 ASCII 化。

**结论**：我们「能导出 VCD」不等于「合规」。最可能的坑是第 3 项（timescale 与 24MHz 对齐）与第 1 项（timescale 取值非法），其次第 4/5 项。建议按上表逐项加自检并至少用一款第三方 VCD 查看器回读验证。

**体积估算公式**（VCD 大量变化点）：
```
size_vcd ≈ header_bytes + Σ_change( len(time_digits) + 1(id) + 1(value) + 1(newline) )
          ≈ header + changes × (digits(total_cycles) + 3)
以 24MHz×2s(48e6 样本)、8 通道、平均翻转率 p 计：
  changes ≈ 8 × 48e6 × p
  p=0.01 → 3.84e6 变化点；位数≈8 → ≈ 3.84e6 × 11B ≈ 42 MB
  p=0.10 → 38.4e6 变化点 → ≈ 422 MB（文本膨胀明显）
```
说明：VCD 对「稳定信号」体积尚可，对「高频翻转」会数倍于原始 48MB；这是选择会话文件用二进制而非 VCD 的原因之一。

## 5. 我们的会话文件格式设计

### 5.1 扩展名与容器

- **扩展名建议**：`.lcaps`（Logic Capture Session）——短、专属、避免与 `.sal`/`.sr` 混淆。
- **容器建议**：**ZIP**（自研最小 ZIP 写入/读取，或用平台内置压缩 API；契约不允许新增第三方依赖，ZIP 是浏览器/Node 原生可处理的成熟格式）。
- **为什么用 ZIP**：
  1. **自描述 + 多文件**：元数据(JSON)、波形(二进制)、解码结果、缩略图、备注可作为独立条目，天然版本化，读取时可按需跳过（`logic.bin` 不解压即可定位）。
  2. **透明兼容**：与 `.sr`/`.sal` 同思路，工具链成熟，能直接 `unzip -l` 检查，便于排错。
  3. **压缩可选且按条目控制**：波形条目可选择 store(不压缩)或 deflate；元数据条目文本压缩收益大。
  4. **大文件友好**：ZIP64 突破 4GB 限制，远超 48MB 需求。
- **为什么不用纯单文件/裸二进制拼接**：单文件需自定义分界与偏移表，读写复杂、易损坏且不可局部访问；裸二进制没有元数据与扩展能力。
- **为什么不用自定义数据库(SQLite)**：引入依赖与二进制布局复杂度，切换/分享不便，得不偿失。

### 5.2 内部结构

ZIP 内条目（建议）：

```
lcaps/                       (可选根目录，便于整体解压)
  meta.json                  元数据（必需，UTF-8 JSON，版本化 schema）
  waveform.bin               波形原始字节流（必需，我们的 8 通道字节格式）
  decoders.json              解码结果（可选）
  view.json                  视图状态（可选：缩放/滚动/通道显隐/标记）
  thumbnail.png              缩略图（可选）
  notes.md                   会话备注（可选，纯文本）
README.txt                  格式说明 + 版本（可选，便于人工识别）
```

- 波形保持我们现有裸字节格式（每字节 8 通道），零转换成本；按条目决定是否 deflate。
- 元数据和视图状态是文本，压缩收益大且可阅读。

### 5.3 元数据 schema

字段（≥12，实际 24 项；类型标注）：

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 1 | `format_version` | int | 会话格式版本，从 1 开始 |
| 2 | `session_id` | string(uuid) | 全局唯一 ID |
| 3 | `session_name` | string | 用户命名 |
| 4 | `created_at` | string(ISO8601) | 采集时间 |
| 5 | `modified_at` | string(ISO8601) | 最后修改时间 |
| 6 | `device` | string | 设备/驱动标识 |
| 7 | `samplerate_hz` | int | 采样率（如 24000000） |
| 8 | `channel_count` | int | 通道数（8） |
| 9 | `channel_names` | array[string] | 每通道自定义名 |
| 10 | `channel_enabled` | array[bool] | 每通道显隐 |
| 11 | `sample_count` | int | 样本数（如 48000000） |
| 12 | `duration_s` | float | 时长（秒） |
| 13 | `trigger_channel` | int\|null | 触发通道 |
| 14 | `trigger_sample` | int\|null | 触发点样本索引 |
| 15 | `trigger_type` | string | rising/falling/both/none |

### 5.4 版本兼容

- `format_version` 为第一字段；读取时先校验。
- **向前兼容**：旧版读取器遇到 `version > 自身` → 提示升级，不静默误读。
- **向后兼容**：新版读取器必须能读所有低版本；未知字段忽略（忽略未知键是 JSON 的自然属性）。
- **变更规则**：新增可选字段 → 小版本；改变已有字段语义/编码 → 大版本 + 迁移函数。
- 可选：在 ZIP 注释写入 `lcaps-v1` 便于无解压识别。

### 5.5 体积估算

以 24MHz×2s = 48,000,000 样本 × 8 通道 × 1B 为例：

```
raw_waveform = 48,000,000 × 1B × 8ch / 8 = 48,000,000 B ≈ 45.8 MiB
ZIP container ≈ local headers/central dir ≈ 1 KB（条目极少）
meta.json     ≈ 2–8 KB（未压缩）
view.json     ≈ 1–20 KB
thumbnail.png ≈ 10–50 KB
decoders.json ≈ 0–500 KB（视解码点数）

case A（波形 store，不压缩，最稳、最快）：
  total ≈ 48,000,000 + ~80 KB ≈ 45.9 MiB
case B（波形 deflate，实际电平多数时间不变，经验 1.5–4x）：
  total ≈ 48,000,000 / 2 + ~80 KB ≈ 23 MiB（保守按 2:1）
case C（极端高频翻转、几乎不可压缩）：
  total ≈ 48.1 MiB（deflate 头开销略增）
```
结论：48MB 量级完全可装下；**默认用 store 保证加载速度与确定性**，提供「压缩保存」选项让用户按存储空间取舍。对比：同数据 VCD 在 p=0.1 时可达 400MB+，故会话文件必须用二进制而非文本。

## 6. 采集历史 UI 设计

- **位置**：页面左侧新增可折叠侧栏「会话 / Sessions」（桌面端常驻，移动端抽屉），与波形画布并列；顶部工具栏加「保存会话 / 打开会话」按钮。
- **每项显示**：会话名、采集时间（YYYY-mm-dd HH:MM:SS）、采样率（24 MHz）、时长（2.00 s）、通道数、缩略波形图（从 thumbnail.png 读取；无则画占位）、标签 chip、 bookmark 数量角标。
- **排序/筛选**：按时间倒序；支持按标签/名称搜索；星标置顶。
- **交互**：
  - 单击：加载该会话（替换当前视图），加载前若当前有未保存改动则提示；

## 7. 对比模式设计

- **入口**：历史列表中选中两个会话 →「对比」；或从会话 A 点「与当前波形对比」。
- **对齐方式**：
  - 默认 **按触发点对齐**（trigger_sample 对齐到同一 x=0），因为两次采集往往触发条件相同、关注触发前后相对时序；
  - 可选 **按时间原点对齐**（样本 0 对样本 0）用于无触发的定时比对；
  - 提供手动偏移微调（± 采样点输入框 + 拖拽）。
- **视觉区分**：
  - 会话 A 用主色（如蓝 #2b6cb0），会话 B 用对比色（如橙 #dd6b20）；
  - 上层波形半透明（alpha 0.55）叠加，或采用「上下分道」（A 在上半区、B 在下半区）两种切换；
  - 图例固定显示两个会话名/颜色块；重叠跳变沿处用加粗描边提示差异；
  - 支持「差异高亮」：仅显示两会话逻辑值不同的区间（异或视图）。
- **导航**：共享缩放/滚动；提供「同步游标」两条时间线同步移动并显示两会话同一时刻的值。
- **限制**：采样率不同的两会话需先重采样或按时间轴（秒）对齐，UI 应提示。

## 8. 导出优先级

8 种格式排序（先做→后做）与理由：

| 优先级 | 格式 | 理由 |
|--------|------|------|
| 1 | **CSV (changes + samples)** | 已有基础，加 samples 模式成本最低，通用性最强 |
| 2 | **JSON 结构化** | 便于二次开发/API，元数据+解码一起导出，前端实现简单 |
| 3 | **VCD（合规化修正）** | 已有实现，按第 3 节修合规即可，生态兼容价值高 |
| 4 | **二进制原始（自描述头）** | 已有基础，加 header 变自描述，作为其他格式中间表示 |
| 5 | **NumPy .npy/.npz** | 数据科学用户常用，header 简单，`.npy` 易做 |
| 6 | **PNG 截图** | canvas 现成能力，用于报告/分享；不可回导，价值中等 |
| 7 | **MATLAB .mat** | 需手写 MAT v5 最小子集，收益面较窄 |
| 8 | **Wavedrom JSON** | 面向文档示意，需大幅降采样，适用场景最小 |

> 第一批（P0）：CSV + JSON + VCD 合规化；第二批：npy + PNG；第三批：mat + Wavedrom。
