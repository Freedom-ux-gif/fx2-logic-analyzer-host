# 触发系统与模拟通道调研

> 目标：用户反馈"功能太少"，本文调研**硬件触发**与**模拟通道**两个方向，判断「业界能做」与「我们这块 0925:3881 八通道纯数字克隆板能做」的边界。核心结论先行：**硬件触发与真实模拟通道我们都做不了**；但**软件触发增强**与**数学通道（虚拟通道）**是纯软件功能，不需要硬件支持，是真正可落地的增长点。所有硬件结论均以实测事实与一手资料为依据，不做无依据的乐观推测。

## 1. 硬件触发

### 1.1 业界做法（fx2lafw / Logic 2 / DSView）

- **fx2lafw（开源 FX2 固件）**：定位就是"simple logic analyzer and/or oscilloscope hardware"的通用固件，支持任意 FX2 板（S1）。它支持 8/16 数字探针（PB0-PB7 / PD0-PD7），**全部使用 24 MHz 晶振**（S1）。其设备表中原版 Saleae Logic 与大量 0925:3881 克隆板都以 8 通道、100% 状态被支持（S1）。
- **sigrok 的触发架构分两层**（S5/S6）：
  - 硬件触发：驱动层若支持，设备自己匹配条件；sigrok 提供 `struct sr_trigger` / `sr_trigger_stage` / `sr_trigger_match` 抽象（S6）。
  - 软件触发：libsigrok 的 `soft-trigger.c` 在**主机侧**对流式数据逐样本匹配，源码明确实现：
    - 触发类型 `SR_TRIGGER_ZERO/ONE/RISING/FALLING/EDGE`（0/1/上升/下降/任意边沿）；
    - 多级 stage：`cur_stage` 逐阶段推进，前一 stage 命中才进入下一 stage，未命中回溯 `i -= cur_stage * unitsize`（S5）；
    - 预触发环形缓冲：`pre_trigger_buffer`，`pre_trigger_append()` 循环覆盖，`pre_trigger_send()` 在命中后回放（S5）。
- **原版 Saleae Logic 在 sigrok 下的触发标注为 `none (SW-only)`**，且无板载缓冲（S2）——即原厂 8 通道 Logic 的 sigrok 路径也是主机软件触发，不是硬件触发。
- **Logic 2 / DSView**：商业软件提供边沿、模式、串行等触发 UI（S4 未取到正文，仅作背景）；DSView 仓库确认有 `DSView/pv` 与用户手册 `ug31.pdf`（S7），其触发是设备相关能力，非 FX2 克隆板普遍具备。

### 1.2 FX2 的触发机制真相

1. **FX2 芯片本身没有"逻辑触发"外设**。Cypress FX2（CY7C68013A）是 USB 2.0 微控制器，采集逻辑在 GPIF / 固件循环里把引脚数据塞进 FIFO 端点。所谓"触发"只能在两条路径之一实现：
   - **固件层硬件触发**：在 FX2 固件中比较采样字节与条件，命中后才开始/停止向端点写数据（需要固件支持并占用 8051 周期，受限于 8051 速度）；
   - **主机软件触发**：设备全量原始数据上送，主机逐样本匹配——这正是 sigrok `soft-trigger.c` 的做法（S5）。
2. fx2lafw 及其配套设备表**没有列出任何触发类型或触发能力字段**（S1），sigrok 对原版 Logic 的结论是 `none (SW-only)`（S2）。
3. **触发深度（预触发样本数）的决定因素**（S5 源码给出精确答案）：
   - 软件触发：由主机**环形缓冲大小 = unitsize × pre_trigger_samples** 决定，本质是**主机内存**问题，想设多大设多大（受内存限制）。`soft_trigger_logic_new()` 里 `g_try_malloc(pre_trigger_size)` 分配（S5）。
   - 硬件触发：由设备板载 FIFO/RAM 容量决定；FX2 内部 FIFO 仅 4×512 字节量级，板上若无外扩 RAM（S1 表格中这类克隆板"Buffer/ESD-protection"多为 74HC245/74HC244 缓冲器而非 RAM），预触发深度极浅。

### 1.3 我们这块板能不能用（结论 + 依据）

**结论：不能用硬件触发。**

依据（全部为已核实事实，非推测）：

1. **协议层**：我们只逆出"设采样率 + 启动采集"一条命令，设备的触发寄存器协议**尚未逆出**（S9 实测）。没有配置触发条件的命令通道，硬件触发无从下发。
2. **固件层**：设备是克隆板，采用通用 FX2 架构（S1 表格中 0925:3881 Clone (Logic) 为 8 通道）；sigrok 对同 VID/PID 的原版 Logic 判定为 `none (SW-only)`（S2），说明这条软件栈上就没有硬件触发接口。
3. **硬件层**：8 通道纯数字、无板载大容量缓存（S1/S9），即便固件支持触发，预触发深度也只能来自主机内存——等价于软件触发。
4. 因此当前实现"先采全量到内存、再离线找触发点、保留预触发"是**唯一可行路径**，与 sigrok 软件触发的环形缓冲思路一致（S5）。

### 1.4 若要试，需要逆什么

只有当用户坚持要试硬件触发时，才需要以下工作（**当前不做，仅列明门槛**）：

1. 从原厂 Logic 软件（或 sigrok 固件源码）逆向出触发配置命令：触发类型寄存器、通道掩码、边沿/电平条件、预触发深度寄存器的**具体字节格式与混淆算法**（我们已知命令需混淆，S9）。
2. 用逻辑分析仪/USB 抓包对比"设置触发"前后上位机发出的 USB 控制传输，确认命令结构。
3. 确认克隆板固件是否**真的实现**了这些寄存器（克隆固件可能阉割）——验证方法：对某通道施加已知边沿，下发触发命令，观察端点 0x82 是否只在边沿后返回数据；若不返回或全量返回，说明固件不支持。
4. 上述任何一步失败即回到软件触发。鉴于工作量大、收益不确定，**建议不投入**。

## 2. 模拟通道

### 2.1 硬件前提

真实模拟通道的前提条件（缺一不可）：

1. **ADC 芯片**：必须有模数转换器把模拟电压量化为数字码（S3 中所有带模拟的设备都为此专门配置了 ADC/模拟前端）。
2. **模拟前端**：输入保护、可编程增益/衰减、量程切换、抗混叠滤波。
3. **数据通道**：FX2 需要有额外引脚/端点把 ADC 采样流送到主机。S1 明确说明："For analog support PD0-PD7 (plus additional hardware) is usually used"——即模拟通道要**占用额外的 PD 口引脚与额外硬件**。
4. **典型规格对照**（S1/S3）：
   - AX-Pro 类克隆板：8 数字 + 1 模拟，模拟带宽 3 MHz；
   - Saleae Logic Pro 16：16 数字 + 16 模拟，模拟 50 MSa/s、5 MHz 带宽；
   - 带示波器功能的 Rigol/Siglent/LeCroy 等：2–4 通道模拟，GSa/s 级。

### 2.2 我们的设备有无可能

**结论：不能。我们的设备没有任何模拟输入能力。**

依据：

1. **大脑实测**：设备为 8 通道纯数字，**没有 ADC**（S9）。
2. **数据与通道结构**：EP 0x82 每字节 8 位对应 8 个数字通道，没有任何模拟码流通道（S9）。
3. **固件证据**：S1 脚注明确："Analog signal support is not yet implemented"（fx2lafw 的模拟支持尚未实现）；另一条脚注："Even though this device has the same USB VID/PID as the CWAV USBee AX-Pro, it only has 8 channels and no analog support"——即**同 VID/PID 不等于有模拟**，这正是我们 0925:3881 克隆板的情况。
4. **硬件资源**：8 通道已占用 PB0-PB7，模拟需额外 PD 口+ADC（S1），而本板无此额外硬件（S9 实测纯数字）。

**严格结论：不能通过软件、驱动、固件升级或"某种方式"获得模拟输入。** ADC 是物理器件，软件无法凭空生成模拟采样。若要模拟通道，只能**换硬件**（购买带 ADC 的设备），这不是本项目范围。任何声称"可能可以"的说法若无 ADC 芯片型号与电路图支持，均属乐观推测，不予采纳。

### 2.3 界面要不要预留

**建议：不预留真实模拟通道 UI，但可以预留"数学通道"的显示框架（见第 3 节）。**

理由：

1. 界面预留模拟通道入口（电压量程、耦合方式、ADC 位数选择）会误导用户以为硬件支持，且这些控件永远无法产生数据——这是虚假功能。
2. 真正能在 UI 上扩展的是**虚拟通道 / 数学通道**：它们看起来像"多出来的通道"，但数据来自已有 8 路数字信号的运算，不依赖硬件。第 3 节详述。
3. 若未来换设备（带 ADC），UI 架构应允许新增 channel type（`analog`），但**当前不给用户可见的空占位**。

## 3. 数学通道（纯软件，重点）

### 3.1 业界能力

- DSView 提供 **math channel**，可对已采集通道做数学/逻辑运算并显示结果波形（S7 确认 DSView 仓库含 `pv` 模块与用户手册 `ug31.pdf`；具体运算类型以 DSView 手册为准）。典型商业逻辑分析仪/示波器的 math channel 能力包括：
  - 算术：加、减、乘、除；
  - 数字通道间的逻辑运算：AND / OR / XOR / NOT / NAND / NOR / XNOR；
  - 信号处理：微分、积分、FFT（通常为示波器高端功能，逻辑分析仪少见）。
- sigrok/PulseView 生态中，解码器可叠加（如 `i2cfilter` 基于 `i2c` 输出再过滤，见 R4 调研 §4.2），本质是"以已有通道/事件为输入生成新视图"——与数学通道思想一致。

### 3.2 我们可实现的清单

以下为**纯软件、不依赖任何硬件**的数学/虚拟通道清单（≥5 项，按价值排序）：

| # | 虚拟通道 | 运算 | 输入 | 价值 | 备注 |
|---|---|---|---|---|---|
| 1 | 任意两通道 AND | `chA & chB` | 2 数字通道 | 高 | 最常用的"总线使能+数据"组合判定 |
| 2 | 任意两通道 OR | `chA \| chB` | 2 数字通道 | 高 | 多路事件合并（如多个中断线） |
| 3 | 任意两通道 XOR | `chA ^ chB` | 2 数字通道 | 中高 | 相位差/边沿检出、曼彻斯特解码前置 |
| 4 | 单通道 NOT | `~chA` | 1 数字通道 | 中 | 反相观察，配合低有效信号 |
| 5 | 总线数值通道 | `ch0..ch7` 按权重合成 0–255 | 2–8 数字通道 | 高 | 把并行总线显示为数值曲线/阶梯波 |
| 6 | 位域切片 | 从总线值取 `[m:n]` 位 | 总线通道 | 中高 | 观察寄存器某几位，减少通道占用感 |
| 7 | 边沿脉冲通道 | 对通道做异或差分 | 1 数字通道 | 中 | 把电平波变成"每边沿一个脉冲" |
| 8 | 频率/周期通道 | 相邻边沿间隔换算 | 1 数字通道 | 中 | 时域测量可视化，配合 PWM 解码 |

### 3.3 实现要点

1. **数据模型**：8 通道数据本质是 `uint8`（每 bit 一通道，S9），逻辑运算可用位运算一次处理整字节——**单个虚拟通道 = 对全流做一次 numpy 位运算**，内存可增量生成，不必全量物化。
2. **组合数量**：8 通道两两组合，有序对 8×7=56、无序对 C(8,2)=28；再叠加 AND/OR/XOR 三种运算，理论可生成 28×3=84 个二元虚拟通道 + 8 个 NOT + 1 个总线值通道。**"功能太少"的抱怨可通过虚拟通道数量显著缓解**，但要注意 UI 分组管理，避免淹没真实通道。
3. **延迟计算**：虚拟通道最好按需计算（用户勾选时才生成），并缓存结果；避免一开始就生成 84 条，浪费内存与 CPU。
4. **时间对齐**：虚拟通道与原始通道共享同一采样时钟/样本索引，天然对齐（沿用现有 `SampleStream.channel_bits` 与样本索引约定，见 R4 调研 §4.3）。
5. **显示**：阶梯波（数字）用于 AND/OR/XOR/NOT；数值曲线用于总线值通道；边沿脉冲用窄脉冲显示。
6. **命名与去重**：通道名建议 `AND(ch0,ch1)` 形式，运算结果可缓存复用（AND 交换律下 `AND(ch0,ch1)` 与 `AND(ch1,ch0)` 为同一通道）。

## 4. 高级软件触发（重点）

硬件触发逆不出，软件触发是当前唯一路径，因此**加强软件触发是性价比最高的方向**。sigrok 的 `soft-trigger.c` 已经实现了多级 stage 与环形预触发缓冲（S5），我们的实现与之同类，可借鉴其结构。

### 4.1 六种高级触发类型

1. **串行协议触发**：等到某个 UART 字节 / I2C 地址出现才捕获。
2. **多级触发**：A 条件满足后再等 B 条件（A→B）。
3. **触发计数器**：第 N 次满足条件才触发。
4. **窗口触发**：信号在指定时间窗口内/外才触发（契约描述为"窗口外才触发"）。
5. **毛刺触发**：脉宽小于 N 个采样点才触发。
6. **状态机触发**：按顺序满足 A→B→C 的序列触发。

### 4.2 每种：难度/可行性/内存开销

前提：当前架构是"先采全量到内存、再离线找触发点"（S9）。因此所有软件触发的**内存开销主体是全量采集缓冲**，与触发类型关系不大；下表"内存开销"指触发算法**额外**需要的状态/结构。

| 触发类型 | 实现难度 | 现有代码能否支持 | 额外内存开销 | 说明 |
|---|---|---|---|---|
| ① 串行协议触发 | **中** | **可**（复用已有 UART/I2C 解码器，见 R4 调研 §5） | 低：解码器状态 + 目标值（字节/地址） | 本质是"解码结果匹配"；全量内存里搜目标事件即可，无需新硬件 |
| ② 多级触发（A→B） | **低中** | **可**（sigrok `cur_stage` 已验证此结构，S5） | 极低：stage 索引 + 每 stage 条件 | 逐阶段推进，命中失败需回溯（S5 的 `i -= cur_stage * unitsize`） |
| ③ 触发计数器（第 N 次） | **低** | **可** | 极低：一个整型计数器 | 每次条件命中计数+1，到 N 才最终触发；易实现 |
| ④ 窗口触发 | **中** | **可**（需时间戳区间判断） | 低：窗口起止样本索引 | 事件需落在 `[t_start,t_end]` 外才触发；用样本索引比较，无额外缓冲 |
| ⑤ 毛刺触发（脉宽<N） | **低中** | **可**（边沿检测+脉宽测量） | 低：上一边沿样本索引 | 复用差分边沿数组（`np.flatnonzero`），量相邻边沿间隔<N 即触发 |
| ⑥ 状态机触发（A→B→C） | **中高** | **可**（②的推广，stage 数≥3） | 低：状态索引 + 条件表 | 比②复杂度高在条件表与回溯；sigrok 多 stage 机制可直接借鉴（S5） |

**共性结论**：六种都能在现有"全量采集 + 离线搜索"架构上实现，**不需要改设备协议、不需要新硬件**。难度从低到高：③ < ⑤ ≈ ② < ④ < ① < ⑥。

### 4.3 推荐优先级

1. **P0：③ 触发计数器 + ⑤ 毛刺触发**——最简单、见效快，直接增加"触发设置"选项数量。
2. **P1：② 多级触发（A→B）**——中等难度，实用价值高，与 sigrok 架构一致。
3. **P2：⑥ 状态机触发**——②的推广，作为 P1 完成后的自然扩展。
4. **P3：④ 窗口触发**——特定场景（时序违规检测）有用。
5. **P4：① 串行协议触发**——依赖解码器质量，价值高但实现与调试成本最高，放最后。

## 5. 明确不能做的（含依据）

| # | 不能做 | 依据（具体原因，非"应该不行"） |
|---|---|---|
| 1 | **模拟通道（真实 ADC 输入）** | 大脑实测无 ADC、无模拟码流通道（S9）；S1 脚注"Analog signal support is not yet implemented"且"同 VID/PID 的克隆板只有 8 通道无模拟"；ADC 是物理器件，软件无法生成——**只能通过换硬件实现** |
| 2 | **硬件触发** | 触发寄存器协议未逆出，无配置通道（S9）；原版 Logic 在 sigrok 下为 `none (SW-only)`（S2）；FX2 无专用逻辑触发外设，固件层触发需逆固件（见 §1.4，当前不做） |
| 3 | **超过 8 通道** | 硬件只有 8 路输入，数据每字节 8 位对应 8 通道（S9）；16 通道需 PD0-PD7 额外引脚与不同板卡（S1），本板无此硬件 |
| 4 | **高于 24 MHz 采样** | 10 档采样率上限为 24M（S9）；S1 明确"All devices use a 24MHz crystal"，FX2 采集受 24 MHz 晶振与 8051/FIFO 带宽限制——这是硬件时钟上限，无法通过软件突破 |
| 5 | **板载大容量预触发缓存** | 克隆板"Buffer/ESD-protection"为 74HC 系列缓冲器而非 RAM（S1 表格），FX2 内部 FIFO 仅数 KB——预触发深度只能来自主机内存，即软件触发 |
| 6 | **软件凭空提升分辨率/模拟精度** | 无 ADC，数字通道只有 0/1 两态（S9）；数学通道只能做数字逻辑运算，无法产生模拟幅度信息 |

---

## 6. 与现有实现的差距

| 现有能力 | 本文调研后的差距 |
|---|---|
| 已逆出"设采样率 + 启动采集"命令 | 缺任何触发配置命令；硬件触发不可行，需在软件侧找补（§1.3/§1.4） |
| 软件触发（全量采集 + 离线找触发点 + 保留预触发） | 只有基础触发；缺 §4 六种高级触发；可借鉴 sigrok 多级 stage 结构（S5） |
| 8 通道数字波形 + 4 个解码器（UART/I2C/SPI/CAN，见 R4） | 缺数学/虚拟通道（§3）；用户"功能太少"的一大半可由此缓解 |
| 无模拟通道、无 ADC | 客观硬件限制，无法在软件内补齐（§2/§5） |

**差距结论**：硬件层面的差距（模拟、硬件触发、>8 通道、>24 MHz）**不可弥合**；软件层面的差距（高级触发、数学通道）**完全可做且投入产出比高**。

---

## 7. 实施建议

按"不依赖硬件、见效快"原则排序：

1. **先做数学/虚拟通道（§3）**：AND/OR/XOR/NOT + 总线值通道，纯位运算，代码量小，立刻把"8 通道"扩展为"8 真实 + 数十虚拟通道"，直接回应"功能太少"。
2. **再做高级软件触发（§4）**：按 P0→P4 顺序，先计数器/毛刺，再多级/状态机，最后串行协议触发；可复用 R4 已有的解码器。
3. **UI 不预留空模拟通道**（§2.3）：避免虚假功能误导用户；可在文档里明确"本设备为纯数字逻辑分析仪"。
4. **不投入硬件触发逆向**（§1.4）：除非用户明确要求且接受高风险；当前证据表明收益极低。
5. **文档化硬件边界**（§5）：把"不能做清单"写进用户文档，管理预期，减少"为什么没有模拟通道"类疑问。

> 一句话总结：**硬件已到天花板，软件还有很大空间**。把资源投在数学通道与高级软件触发上，而不是追求这台克隆板做不到的模拟通道和硬件触发。
